# krx-screener 백엔드 설계

> 상태: 구현됨 (2026-11-07 기준). 이 문서는 설계 기준이고, 구현이 설계와 다르거나 설계에 없던 결정은 14장에 모았다. · 작성일: 2026-11-06
> 범위: 백엔드(웹 주소 API)만 다룬다. 화면은 이 API를 부르는 것이고 [화면 명세](frontend-spec.md)에 있다.
> 관련: [README](../README.md) (실행 방법) · [용어집](../GLOSSARY.md) · [API 테스트 방법](api-testing.md) · [ADR 0001 PostgreSQL](adr/0001-postgres-analysis-queue.md)

## 1. 한 줄 요약

코스피·코스닥 전종목에서 분석할 종목 목록을 뽑고(1), 목록을 나눠서 TradingAgents-KR로 분석하고(2), 처리 여부와 점수를 조회하고(3), 전부 끝나면 점수로 순위를 매겨 정리한다(4).

## 2. 기능 네 개

| # | 기능 | 한 줄 설명 |
|---|---|---|
| 1 | 목록 뽑기 | 분석 대상 전체 목록을 만들고 세션 값을 붙인다 |
| 2 | 나눠서 처리 | 세션 + 오프셋으로 목록의 한 구간을 분석한다 |
| 3 | 조회 | 세션의 전체 목록과 처리 여부·등급·점수를 보여준다 |
| 4 | 정리 | 세션이 전부 끝났을 때만, 종목끼리 비교해 순위를 매긴다 |

모든 기능은 **언제든 실행**할 수 있다. 정해진 요일이나 시간 제한은 없다. 사용량을 보면서 사용자가 직접 호출한다.

## 3. 세션

- 목록을 뽑을 때마다 세션이 하나 생긴다. 이번 주 목록과 다음 주 목록은 서로 다른 세션이다.
- 세션 값은 **UUID + 일자 데이터**다. UUID는 세션을 구분하고, 일자(기준일, 뽑은 시각)는 따로 저장한다.
- 화면에는 `일자-UUID 앞 8자리`(예: `2026-11-06-3f2a9c1b`)로 줄여 보여준다.
- 같은 날 목록을 여러 번 뽑아도 UUID가 달라서 섞이지 않는다.
- 2·3·4번은 세션 값을 받는다. 값 자리에 `latest` 를 주면 가장 최근 세션이다.
- 세션은 기준일 하나로 고정된다. 세션 안의 종목은 모두 그 기준일의 시세로 분석한다.

## 4. 기능 1 — 목록 뽑기

기준일의 시세만으로 종목을 줄인다. 모델도 계정도 쓰지 않는다.

**유니버스에서 제외**: 우선주, 스팩, 관리종목, 거래정지 의심(기준일 거래량 0 또는 시세 없음), 신규상장 60거래일 미만(평일 수로 근사), 리츠.
**제외하지 않고 표시만**: 투자주의환기종목, 외국기업.

**필터 (세 조건을 모두 만족)**
- 20거래일 평균 거래대금 10억 원 이상. 거래대금은 종가 × 거래량으로 근사한 값이다.
- 종가가 20일선 위
- 종가가 60일선 위

RSI 조건은 두지 않는다. 2026-11-05 기준으로 이 조건이면 **116개**다.

**수급**: 필터를 통과한 종목에만 조회해서 **표시만** 한다. 후보를 거르지 않는다. 출처는 네이버 증권(비공식)이고 최근 5거래일 외국인·기관 순매수 합계의 부호로 상태를 정한다 — 양호(둘 다 매수 우위) · 부분(한쪽만) · 약함(둘 다 아님) · 미확인(읽지 못함). 미확인은 수급 0이 아니며 탈락 사유도 아니다.

**종목마다 저장하는 값**: 종목코드, 종목명, 시장, 순번(거래대금 큰 순서, 1부터), 종가, 평균 거래대금(근사), RSI, 수급 상태와 5거래일 순매수 합계, **업종 코드, 업종명, 기업 설명**.

업종명과 기업 설명은 "테마를 비교할 수 있는 최소한의 텍스트"다. 출처는 네이버의 다음 주소이고 로그인 없이 읽힌다.

```
GET https://stock.naver.com/api/domestic/detail/{종목코드}/detail?codeType=KRX
  upjongCode(업종 코드), upJongName(업종명), comment1~3(기업 설명)
```

업종 코드는 값이 있으면 저장해서 쓰고, 없으면 빈 칸이다. 이 주소는 투자 테마 이름(예: HBM)이 아니라 **업종**(예: 반도체와반도체장비)을 준다. 비공식 주소라서 바뀔 수 있고, 못 읽은 종목은 빈 칸으로 둔다.

## 5. 기능 2 — 나눠서 처리

- **입력**: 세션, 오프셋(목록 앞에서 건너뛸 개수), 개수. 개수는 고정이 아니다.
- **동작**: 목록의 오프셋 위치부터 개수만큼, 종목을 **한 개씩 순서대로** TradingAgents-KR에 보내 분석한다. 이미 끝난 종목과 **실패한 종목은 건너뛴다** (#77). 대기 종목과, 처리하던 서버가 죽어 `처리 중` 으로 남은 종목만 보낸다.
- **호출하면 바로 "시작했다"고 응답하고 처리는 뒤에서 한다.** 종목마다 약 5분이 걸려서 응답을 기다릴 수 없다. 진행 상황은 3번(조회)으로 본다.
- **같은 세션을 동시에 처리하지 못한다.** 이미 처리 중이면 두 번째 호출은 바로 거절하고 "이미 처리 중"이라고 알려준다. 처리가 중간에 죽어도 잠금이 남지 않게 한다.
- **종목 하나를 끝낼 때마다**: 분석 상태 로그에서 에이전트별 등급을 읽어 저장하고(6장), 그 종목의 점수를 계산해 저장한다. 최종 등급, 분석한 시각, 보고서 번호도 저장한다.
- **실패**(오류, 시간 초과)는 실패로 표시한다. 실패한 종목은 구간 처리가 보내지 않는다 (순번이 앞선 실패 종목이 안 돌린 대기 종목보다 먼저 돌아 쿼터와 시간을 쓰던 것을 막는다, #77). 다시 돌리려면 **`POST /api/sessions/{id}/process-failed`** 를 부른다: 구간 없이 세션 전체의 실패한 종목을 순번 순서대로 처리하되, **종목마다 먼저 서버에 같은 종목·기준일의 끝난 보고서가 있는지 보고 있으면 새로 보내지 않고 그 결과를 저장한다** (#75, 13장). 없는 종목만 새로 보낸다. 서버가 받지 않는 영숫자 코드(숫자 6자리가 아님)는 뺀다. 같은 세션 잠금(409)·서버 상태 확인(503)·응답 모양(`202/200 {"started", "queued"}`)은 구간 처리와 같다. 새로 보내는 종목만 쿼터를 쓴다.
  - 분석 상태 조회(GET)가 한 번 끊겼다고 실패로 표시하지 않는다: 2초 간격으로 3번까지 다시 시도하고, 그래도 안 될 때만 실패로 표시한다 (#75, 13장). 사유에는 서버에서는 분석이 끝났을 수 있다는 말과 끊긴 예외의 종류가 들어간다.
- 분석 설정은 항상 `low`로 고정이다. 저장하지 않는다.

## 6. 평가점수

- 에이전트가 낸 등급을 숫자로 바꾼다: 매수 +2, 비중 확대 +1, 보유 0, 비중 축소 −1, 매도 −2.
- **점수 = 등급을 낸 에이전트 전부의 평균** (−2 ~ +2). 비중은 모두 같다.
- 강세·약세 에이전트도 포함한다. 둘의 값은 종목마다 달라서 평균에 넣는다.
- 등급이 없는 에이전트는 평균에서 뺀다. 읽지 못했을 때 점수를 지어내지 않는다.
- 점수는 에이전트의 등급만으로 계산한다. 보고서 본문을 읽고 평가하지 않는다. 모델을 다시 부르지 않으니 쿼터도 들지 않는다.

**에이전트별 등급을 읽는 방법**: 서버가 분석 상태를 JSON 로그로 저장하는데, 에이전트마다 정해진 이름의 칸에 들어 있다. 시세·뉴스·재무 분석가, 강세, 약세, 리서치 매니저, 공격적·보수적·중립 분석가, 포트폴리오 매니저다. 칸이 에이전트를 정하므로 줄 순서로 짐작할 필요가 없다.

```
~/.tradingagents/logs/{종목코드}/TradingAgentsStrategy_logs/full_states_log_{기준일}.json
```

- 서버와 같은 컴퓨터에서 실행한다는 전제다. 이 파일은 서버 API로는 받을 수 없다.
- 같은 종목을 같은 기준일로 다시 분석하면 파일이 덮어써지므로, **분석이 끝난 직후에** 읽는다.
- 에이전트 칸은 10개다. 감성 분석가와 트레이더에는 5단계 `등급`이 없어 읽지 않는다.
- 이 컴퓨터의 실제 로그 13개(종목 9개, 기준일 2024-01-05~2026-11-06)에서 같은 구조(최상위 칸 13개, 에이전트 칸 이름)였고, 포트폴리오 매니저 칸의 등급이 로그의 `final_rating` 과 13개 모두 같았다.
- 칸 안의 글에서는 `등급` 라벨(리서치 매니저는 `추천` 도)의 5단계 값만 읽는다. 표기는 `**등급**: 매수`, `**등급: 보유.**`, `Aggressive Analyst: **등급**: 보유`, 표 `| **등급** | **보유** |`, 영어 대문자(`HOLD`) 등 제각각이다.
- `최종 거래 제안`은 읽지 않는다. 등급을 3단계로 뭉갠 값이라(비중 축소 → 매도) 5단계 등급 대신 쓰면 점수가 치우친다. 그 값만 있는 칸은 비워 둔다.
- 한 칸에 서로 다른 값이 나오면 비워 둔다. 5단계에 없는 값(`REDUCE`)은 읽지 않는다. 로그가 없거나 깨졌거나 다른 종목·기준일의 것이면 에이전트별 등급 전체가 빈다.
- 마크다운 보고서는 `등급:` 줄 개수가 1~13개로 제각각이라 쓰지 않는다.

## 7. 기능 3 — 조회

세션의 **전체 목록을 그대로** 보여주고, 종목마다 처리 여부가 같이 표시된다.

| 구분 | 값 |
|---|---|
| 식별 | 세션, 순번, 종목코드, 종목명, 시장 |
| 테마 | 업종명, 기업 설명 (업종 코드는 저장만) |
| 1단계 | 수급 상태, 종가, 평균 거래대금, RSI |
| 처리 | 처리 여부(대기·처리 중·완료·실패), 분석한 시각, 실패 사유, 보고서 번호 |
| 결과 | 최종 등급, 평가점수, 순위 |

- 점수는 2번이 끝난 종목부터 보이고, **순위는 4번을 실행한 뒤**에 채워진다.
- 처리 여부로 걸러 보거나 점수·순위로 정렬할 수 있다.

## 8. 기능 4 — 정리

- **세션의 모든 종목이 처리된 뒤에만 실행**된다. 하나라도 남아 있으면 실행하지 않고 남은 개수를 알려준다.
- 실패한 종목은 실패로 표시한 채 **비교에서 제외**한다. 별도의 제외 처리는 만들지 않는다.
- 끝났지만 점수가 없는 종목(에이전트 등급을 하나도 읽지 못함)도 순위에서 뺀다. 점수를 0으로 지어내지 않기 위해서다. 정리 응답의 `unscored` 가 그 개수다.
- 처리 중인 세션(처리 잠금이 잡힌 세션)은 정리하지 않는다. 정리하는 동안 같은 잠금을 쥐어서 점수가 바뀌지 않게 한다.
- 종목끼리 점수를 비교해 **점수가 높은 순서로 순위**를 매긴다. 상대 등급이나 동점 묶기는 만들지 않는다. 점수가 같으면 순번(거래대금 큰 순서)이 앞선 종목이 위다.
- 4번을 실행한 뒤에 종목을 다시 분석하면 순위를 "낡음"으로 표시하고, 4번을 다시 실행해야 최신이 된다.
- **정리할 때 업종(테마)별 해석과 종합 평가를 DB 에 저장한다.** 순위와 같은 트랜잭션이라 하나가 실패하면 순위·정리 시각·요약이 모두 이전 그대로다. 다시 정리하면 지우고 새로 넣는다.
  - **저장한 요약을 읽는 곳 두 개**: 세션 조회 응답의 `summary`(`SummaryOut`, 정리하기 전에는 `null`)와 마크다운 보고서 `GET /api/sessions/{id}/report`(정리하기 전에는 `409`). 화면은 `summary` 로 "정리 요약" 카드를 그리고 보고서 링크를 건다.
    등급·수급 분포의 키는 API 가 한국어 표기로 바꿔 순서를 고정해 내려준다 (DB 의 jsonb 는 키 순서를 지키지 않고, 저장값은 영어 코드값이다).
  - **보고서는 저장한 문장을 그대로 싣는다** (`summary_report.py`). 문장을 다시 만들지 않아 화면과 같은 문장이고, 저장한 뒤 문장 틀이 바뀌어도 정리했을 때의 문장이다. 낡은 요약이면 보고서 머리에 그렇게 적는다.
  - 보고서는 마크다운 하나다 (HTML·PDF 는 만들지 않았다).
  - **테마 = 네이버 업종**(`sector_code`/`sector_name`)이다. 투자 테마 이름은 저장하지 않으므로 쓰지 않는다. 업종을 읽지 못한 종목은 `업종 미확인`(`theme_code = ''`)으로 묶는다.
  - **수치로만 만든다.** 모델도 외부 조회도 쓰지 않는다 (`summary.py`). 업종마다 순위에 들어간 종목(끝났고 점수가 있는 종목)의 개수·평균 평가점수·등급 분포·평균 RSI·수급 상태 분포·외국인/기관 5일 순매수 합계를 계산해 정해진 문장 틀에 채운다. 수급을 읽지 못한 종목은 합계에서 빼고(0 으로 치지 않고), 하나도 못 읽었으면 합계는 비운다.
  - 해석 문장은 업종 평균을 **후보 전체 평균과 견준다**: 0.2 이상 높거나 낮으면 "높습니다·낮습니다", 아니면 "비슷합니다". 종목이 3개 미만이면 "참고만 하세요" 를 붙인다. 두 기준 모두 백테스트로 정한 값이 아니라 문장을 읽기 쉽게 하려는 값이다 (`summary.COMPARE_GAP`, `MIN_THEME_SIZE`).
  - **종합 평가**는 후보의 평균 평가점수·등급 분포·수급 분포에, 목록을 만들 때 저장한 **전종목 수치**(`sessions.universe_stats`: 시세를 확인한 종목 수와 조건별 불충족 수 등)를 더한다. 전종목 수치는 시세를 다 읽는 목록 만들기 때만 알 수 있어서 그때 저장한다. 이 기능 전에 만든 목록은 수치가 없어, 종합 평가가 "전종목 수치가 저장되어 있지 않다"고 말한다 (지어내지 않는다).
  - 종합 평가는 "후보는 시장 전체를 대표하지 않는다"는 문장을 늘 붙인다. 후보는 거래대금·이동평균선 조건을 통과한 종목이라서다.
  - 저장 위치(스키마 v5): `session_theme_summaries`(업종별 한 줄), `session_market_summaries`(세션당 한 줄), `sessions.universe_stats`.
  - 낡음은 "다시 정리하면 순위가 달라질 수 있다"는 뜻이다. 정리할 때 순위가 있던 종목이 다시 분석됐거나(점수가 바뀌었거나 실패해 빠져야 함), 순위 밖이던 종목이 이제 점수와 함께 끝난 경우다. 실패했던 종목이 또 실패한 재시도처럼 순위가 같을 수밖에 없는 경우는 낡음이 아니다.

## 9. 저장

- **PostgreSQL**에 저장한다. 읽는 쪽(화면)과 쓰는 쪽(처리)이 동시에 있어도 DB가 알아서 처리한다.
- Postgres 서버가 떠 있어야 한다. 접속 정보는 환경변수로 받는다 (코드나 설정 파일에 넣지 않는다).
- 세션 → 종목 → 에이전트 순서로 저장한다. 종목 줄에는 4번의 값과 처리 상태를, 에이전트 줄에는 에이전트별 등급을 둔다.
- **같은 세션 동시 처리 잠금**은 Postgres의 세션 단위 잠금(advisory lock)을 쓴다. 잠금을 잡은 연결이 끊기면 자동으로 풀리므로, 처리가 중간에 죽어도 잠금이 남지 않는다.
- **보고서 본문은 저장하지 않는다.** 서버가 자기 폴더에 갖고 있고, 나중에 볼 일이 생기면 그때 저장한다.
- DB에는 다시 만들 수 없는 분석 결과가 들어간다. 백업은 사용자가 한다.

## 13. 알려진 한계

- 점수는 한 번 돌린 값이다. 같은 입력으로 다시 돌리면 달라질 수 있다: 셀트리온 2026-11-05 는 첫 분석이 +0.20(비중 확대 3·비중 축소 1), 다시 분석이 +0.40(매수 2·비중 확대 1·비중 축소 1)이었다 (최종 등급은 둘 다 보유). 펩트론은 같은 날 3번 다 같았다.
- **상태 조회가 끊겨 실패로 기록된 분석** (#75): 2026-11-07 실제 서버로 116종목을 돌리는 동안 분석 4건이 `ConnectionError` 로 실패로 기록됐는데, 서버에서는 4건 모두 분석이 끝나 있었다 (서버의 분석 상태 로그 수정 시각이 실패 기록 시각보다 뒤였다). 원인으로 폴링 간격(5초)과 uvicorn keep-alive 기본값(5초)이 같아 서버가 막 닫은 연결에 요청을 보내는 경쟁이 유력하고, 같은 방식으로 서버를 두드리면 5초 간격에서 요청 480건 중 2건이 `Connection reset by peer` 로 끊기는 것을 재현했다 (3초 간격은 600건 중 0건). 그러나 실제 비율(분석 약 3%)과 재현 비율(분석 하나에 약 20%)이 맞지 않아 **이것이 원인의 전부라고 단정하지 못한다.** 그래서 상태 조회(GET)만 2초 간격으로 3번까지 다시 시도하고(`analysis.SNAPSHOT_RETRIES`, `RETRY_WAIT_SECONDS`), 사유에 예외의 속 종류(예: `ConnectionError (ProtocolError → ConnectionResetError)`)를 남긴다. 분석 시작(POST)은 다시 시도하지 않는다 (서버가 분석을 하나 더 시작한다). 이미 실패로 기록된 건은 **"실패한 종목 다시 처리" 가 서버의 끝난 보고서를 먼저 찾아 가져온다** (쿼터 0): TradingAgents-KR 의 `GET /api/reports?ticker=&trade_date=` (#174)가 `run_id` 없이 보고서 번호·최종 등급·에이전트별 등급을 주기 때문에 `run_id` 를 저장하지 않는 규칙을 건드리지 않는다 (`analysis.find_finished_report`, `processing.recover_item`). 같은 종목·기준일의 보고서가 여럿이면 **저장 시각이 가장 늦은 것**을 쓴다 (사용자 결정). 한계: 이 서버 기능이 없는 옛 TradingAgents-KR(필터·`trade_date` 없음)에서는 찾지 못해 예전처럼 새로 분석한다 (쿼터). 설정이 다른 분석(서버 화면에서 직접 돌린 것 등)도 같은 종목·기준일이면 가져온다. 가져온 종목은 분석 시간을 재지 않아 `elapsed_seconds` 를 건드리지 않는다.
- **시간 초과 뒤 재시도**: 서버에 취소 API 가 없어서, 기다리기를 멈춘(시간 초과로 실패 처리한) 분석은 서버에서 계속 돌아 보고서까지 저장한다. 같은 종목을 그냥 다시 보내면 서버가 거절하지 않고 새 분석을 하나 더 시작해서 쿼터를 한 번 더 쓴다 (2026-11-07 실제 서버로 확인). 그래서 **보내기 전에 서버의 분석 목록(`GET /api/runs`)에서 같은 종목·기준일의 `pending`/`running` 분석이 있는지 보고, 있으면 새로 보내지 않고 그 분석을 이어서 기다린다** (#70, `analysis.run_one`, 웹·명령줄 공통). 한계: 서버가 재시작되면 목록이 비어 있어 확인할 수 없고, 분석 목록을 읽지 못하면 예전처럼 새로 보낸다(경고 로그). 응답에 `effort`·`analysts` 가 없어서 설정이 다른 분석(예: 사람이 서버 화면에서 돌린 것)도 이어받을 수 있다. 이어서 기다린 종목의 `elapsed_seconds` 는 이어서 기다린 시간만 잰다.
- ~~쉬는 중인 화면은 자동으로 갱신하지 않는다~~ — 쉬는 중에도 30초마다(탭이 보일 때만) 확인해서 다른 탭·API·명령줄이 시작한 처리를 알아챈다 (#71). 한계: 보고 있는 세션의 상태만 확인하므로 다른 곳에서 새 세션을 만든 것은 새로고침해야 보이고, 쉬는 중 확인마다 세션 전체(종목 수십~백여 개)를 내려받는다 (크기는 측정하지 못했다).
- 날짜가 바뀌면 같은 종목의 등급이 바뀔 수 있다 (삼성E&A는 11-05 보유, 11-06 비중 축소). 한 세션은 기준일 하나로 고정된다.
- 쿼터 소모량을 측정하지 못했다. 서버가 토큰 사용량을 기록하지 않아 사용량 화면의 변화로만 알 수 있다.
- 종목당 약 5분(3개 평균 313초)이다. 116개를 모두 보내면 약 10시간이다.
- 업종명은 투자 테마 이름이 아니다.
- Postgres 서버가 꺼져 있으면 목록 뽑기, 처리, 조회가 모두 동작하지 않는다 (서버는 뜨고 화면이 한국어 오류로 알려준다).
- 서버에 로그인이 없다. 이 컴퓨터에서만 쓰는 것을 전제로 하고, 밖으로 열면 접속한 누구나 분석(쿼터 사용)을 시작할 수 있다.
- 평가점수는 좁은 구간에 몰린다 (실제 로그 13개에서 −0.9 ~ +0.4). 종목끼리 견주는 용도이고 절대 기준으로 쓰기에는 값이 작다. 웹 화면은 읽기 쉽게 저장값에 100 을 곱한 정수로 보여 준다 (#76). 저장값·API·정렬·순위는 −2 ~ +2 그대로이고, 몰리는 모양은 같다.
- 네이버 주소 두 개는 비공식이라 바뀔 수 있다. 읽지 못한 값은 빈 칸이다.
- 에이전트별 등급 칸 구조는 이 컴퓨터의 로그 13개로 확인했다. 다른 컴퓨터나 서버 버전의 로그는 확인하지 못했고, 서버가 글 모양을 바꾸면 그 칸이 빈다 (오류로 멈추지는 않는다).

## 14. 구현 상태와 설계와의 차이

2026-11-07 기준으로 이 설계의 기능 네 개와 화면 연결이 구현되어 있다. 웹 처리 경로는 2026-11-07 실제 TradingAgents-KR 로 끝까지 확인했다: 종목 3개 연속 처리·순위 정리, 시간 초과 뒤 재시도, 처리 중 화면 갱신 (`work_history/2026-11-07-59-real-server-check.md`).
확인하지 못한 것은 실패한 분석(서버가 오류로 끝나는 경우)을 실제 서버로 낸 것과, 서버 로그 폴더가 다른 컴퓨터에 있는 경우다.

| 설계 | 주소 | 구현 (`src/krx_screener/`) |
|---|---|---|
| 1 목록 뽑기 | `POST /api/sessions`, `GET /api/sessions` | `routes_sessions.py`, `session_build.py`, `listing.py` |
| 2 나눠서 처리 | `POST /api/sessions/{id}/process` | `routes_sessions.py`, `processing.py`, `analysis.py` |
| 2' 실패한 종목 다시 처리 | `POST /api/sessions/{id}/process-failed` | `routes_sessions.py` (`_start_processing` 을 구간 처리와 같이 쓴다) |
| 6 평가점수 | (처리 안에서 계산) | `agent_ratings.py`(에이전트별 등급 읽기), `scoring.py` |
| 3 조회 | `GET /api/sessions/{id}` (`id` 자리에 `latest` 가능) | `routes_sessions.py` |
| 4 정리 | `POST /api/sessions/{id}/organize` | `routes_sessions.py`, `repository.py`, `summary.py` |
| 4' 정리 요약 보고서 | `GET /api/sessions/{id}/report` (세션 조회의 `summary` 도 같은 요약) | `routes_sessions.py`, `summary_report.py` |
| 상태 확인 | `GET /api/health` | `api.py` |
| 저장 | PostgreSQL (스키마 v4) | `db.py`, `repository.py` |
| 화면 | `krx-screener serve` → `/` | `server.py`, `frontend/` |
| 명령줄 분석 대기열 | `run`·`analyze`·`list` | `analysis_queue.py`, `cli.py` |

설계와 다르거나 설계에 없던 결정 (자세한 이유는 `work_history/` 의 해당 기록):

- **목록은 뒤에서 만들고 진행을 저장한다 (#56).** `POST /api/sessions` 는 기준일을 확인한 뒤 빈 세션(`build.state = "building"`)을 만들어 `202` 로 바로 답하고, 시세 → 수급 → 업종·기업 설명을 백그라운드에서 만든다.
  진행(`build.stage`, `done`, `total`)은 DB 의 세션 행에 적는다(2초에 한 번, 단계가 바뀔 때·끝날 때는 언제나). 서버를 여러 개 띄워도, 서버를 다시 켜도 같은 값을 읽는다.
  - 상태는 `building` → `ready`(끝) / `failed`(오류, `build.error` 에 한국어 이유)이고, `building` 인데 만드는 잠금(어드바이저리 잠금)이 없으면 서버가 죽은 것이라 응답에서 `interrupted`(중단됨)로 바꿔 준다.
  - 같은 기준일을 이미 만드는 중이면 `409 {"detail": …, "session_id": …}`. 잠금을 먼저 잡고 행을 넣으며, 부분 유일 인덱스(`sessions_building_as_of_idx`)가 한 번 더 막는다.
  - 같은 기준일을 다시 뽑으면 못 끝낸 목록(실패·중단)은 지우고 새로 만든다. 만드는 중인 목록에는 처리(`process`)·정리(`organize`)가 `409` 다.
  - 종목 저장이 실패하면 이전과 달리 세션이 `failed` 로 남는다 (이전에는 세션이 남지 않았다).
- **세션이 목록을 뽑을 때 쓴 조건을 저장한다 (#57).** `sessions.criteria`(jsonb, 스키마 v4)에 필터 값·제외한 종류·수급 방식을 값 그대로 넣고(`config.criteria_of`), 세션 응답의 `criteria` 로 내려준다.
  한국어 문구는 서버가 만들지 않고 화면이 만든다. `NULL`(= 응답의 `null`)은 조건 기록 없음이다: 스키마 v4 이전의 세션과 명령줄 세션이 그렇다 (옛 세션을 지금 설정으로 채우면 틀린 값일 수 있어서 채우지 않았다).

- **점수가 없는 종목은 순위에서 뺀다.** 끝났지만 에이전트 등급을 하나도 읽지 못한 종목은 점수를 0으로 지어내지 않고 순위를 비운다. 정리 응답의 `unscored` 가 그 개수다 (8장, `2026-11-07-24-organize-api.md`).
- **정리도 처리 잠금을 쥔다.** 처리 중인 세션은 정리하지 않는다 (같은 문서).
- **"낡음"의 정의**를 순위가 달라질 수 있는 경우로 좁혔다 (8장, `2026-11-07-25-rank-stale.md`).
- **보고서 번호는 서버의 진행 이벤트(`report_saved`)에서 읽는다.** 보고서 목록으로는 이번 분석을 가릴 수 없다 (`2026-11-07-20-report-id.md`).
- **에이전트별 등급**은 `등급` 라벨(리서치 매니저는 `추천`)의 5단계 값만 읽는다. 3단계로 뭉갠 `최종 거래 제안`은 읽지 않고, 한 칸에 서로 다른 값이 나오면 비운다 (6장, `2026-11-07-21-agent-ratings.md`).
- **영숫자 종목코드**는 목록에 들어가지만 서버가 받지 않아 처리할 때 실패(사유 "숫자 6자리만 받음")로 표시된다.
- **명령줄 대기열도 같은 저장소**다: 기준일마다 `source = 'cli'` 세션 하나이고 웹 화면의 세션 목록에도 보인다. 상태는 `pending/running/done/failed` 이고, 후보에서 빠진 끝난 분석은 지우지 않고 보관한다.
  SQLite 와 `--db` 는 없어졌고 `analysis.csv` 의 `run_id` 열은 `report_id` 가 되었다 (`2026-11-07-12-replace-sqlite.md`).
- **서버는 로컬 전용**이다: `krx-screener serve` 는 기본 `127.0.0.1:8100` 이고, 로그인이 없어 밖으로 열려면 `--allow-remote` 가 필요하다 (`2026-11-07-26-serve-frontend.md`).
- **DB 에 `db init` 을 안 한 상태**(스키마가 오래됨)에서는 서버 오류 대신 한국어 안내(503)를 한다.
- **화면의 필터 문구는 고정 글자**다. 지금 `config.yaml` 과 같지만, 세션이 목록을 뽑을 때 쓴 조건을 저장하지 않아 설정을 바꾸면 틀려진다. 세션에 조건을 저장하는 후속 작업이 필요하다 (`2026-11-07-28-screen-api-check.md`).
