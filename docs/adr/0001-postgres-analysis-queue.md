# 세션·분석 대기열·결과는 PostgreSQL에 저장한다

처음에는 "DB 없이 파일(CSV)로 한다"고 정했고, 이어서 SQLite 파일 하나로 바꿨다. 그러나 백엔드가 **웹 주소(API)로 화면에 서비스되는 구조**로 확정되어, 화면이 읽는 동안 처리가 계속 쓰게 되었다. 그래서 사용자가 PostgreSQL로 정했다. SQLite 결정은 구현 전에 이 결정으로 대체되었다.

## Considered Options

- **CSV 파일**: 가장 단순하지만 처리 중·대기 같은 상태가 없고 종목끼리 비교하거나 날짜를 넘어 조회하기 어렵다.
- **SQLite**: 서버가 필요 없고 의존성이 없다. 하지만 화면이 읽는 동안 처리가 쓰면 WAL 모드가 필요하고, 다른 컴퓨터에서는 접근할 수 없다. 이 규모에서는 충분했지만, 백엔드가 서버 구조로 가면서 이점이 줄었다.
- **PostgreSQL**: Postgres 서버를 띄워야 하지만, 동시 읽기·쓰기와 잠금을 DB가 처리한다. 서버를 띄우는 방법(도커 등)은 사용자가 정한다.

## Consequences

- Postgres 서버가 꺼져 있으면 목록 뽑기, 처리, 조회가 모두 동작하지 않는다. 접속 정보는 환경변수로 받는다.
- 같은 세션 동시 처리 금지는 Postgres의 세션 단위 잠금(advisory lock)으로 한다. 잠금을 잡은 연결이 끊기면 자동으로 풀려서, 처리가 죽어도 잠금이 남지 않는다.
- 재분석이 실패해도 이미 있는 등급은 지우지 않는다 (이전 결정 유지).
- DB에는 다시 만들 수 없는 분석 결과가 들어간다. 백업은 사용자가 한다.
- 명령줄(`run`·`analyze`·`list`)의 분석 대기열도 같은 PostgreSQL 세션 저장소로 옮겼다 (#12). SQLite 저장소(`store.py`)와 `--db` 옵션은 없어졌다.
  대기열은 기준일마다 `source = 'cli'` 세션 하나이고(`src/krx_screener/analysis_queue.py`), 웹 화면의 세션 목록에도 보인다.
  후보에서 빠진 끝난 분석은 지우지 않고 보관(`archived`)한다. 기존 SQLite 파일(`krx-screener.db`)은 변환하지 않는다: 그 안의 시범 결과 3개는
  `results/<기준일>/analysis.csv`(DB 에서 내보낸 사본)에 있어서, 그 기준일을 처음 등록할 때 자동으로 가져온다.
