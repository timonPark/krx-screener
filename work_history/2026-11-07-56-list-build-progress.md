# [feat] 목록 뽑기 진행 표시 (#56)

- 브랜치: feat/56-list-build-progress (main 위)
- 작업일: 2026-11-07
- 요청: #56 "목록 뽑기 진행 표시". 설계안(A: 바로 202, 뒤에서 만들고 진행은 세션의 `build` 로 본다)을 보여 드렸고 "특별한 의견 없어요" 로 그대로 진행.

## 수행한 변경

- **DB (스키마 v3, 더하기만)**: `sessions` 에 `build_state`(`building|ready|failed`, 기본 `ready`), `build_stage`, `build_done`, `build_total`, `build_error`. 기본이 `ready` 라서 기존 세션은 그대로 완성된 세션이다.
  같은 기준일의 만드는 중인 웹 세션을 하나로 막는 부분 유일 인덱스 `sessions_building_as_of_idx`.
- **저장소**: `create_building_session`, `set_build_progress`, `finish_build`(종목 저장과 `ready` 표시를 한 트랜잭션), `fail_build`, `building_session_id`, `discard_unfinished`, `effective_build_state`(만드는 중인데 잠금이 없으면 `interrupted`).
- **목록 만들기(`listing.py`)**: `progress(단계, 한 개수, 전체)` 콜백. 단계는 `prices → flow → sector`. 개수는 **끝난 순서**로 센다 (`screen.map_with_progress`, 아래 "이슈에 없던 결정").
- **`session_build.py`(새)**: 뒤에서 목록을 만들고 진행을 DB 에 적는다 (`progress_interval` 초에 한 번, 단계가 바뀔 때·끝날 때는 언제나). 오류는 `failed` + 한국어 이유.
- **API**: `POST /api/sessions` → `202` (기준일 확인은 먼저 하므로 422·503 은 세션이 생기기 전에 그대로 난다). 같은 기준일을 만드는 중이면 `409 {"detail", "session_id"}`.
  같은 기준일을 다시 뽑으면 실패·중단된 목록을 지운다. 세션 응답에 `build {state, stage, done, total, error}`. 만드는 중·실패·중단된 목록의 처리·정리는 `409`.
- **화면(`frontend/`)**: "목록을 만드는 중입니다" 카드(단계·`N / 전체`·막대), 세션 선택의 "· 만드는 중/실패/중단됨", 만드는 중 폴링(2초)과 끝나면 목록 갱신, 처리 시작·정리 막기, 409 시 만드는 중인 세션으로 이동. 예시 모드(`mock.js`)도 같은 모양으로 흉내 낸다.
- **문서**: README, `docs/backend-design.md`(14장), `docs/frontend-spec.md`, `frontend/README.md`, `docs/api-testing.md`(스키마 v3).

## 설계 결정

- **진행은 DB 에 둔다** (메모리 아님): 서버를 다시 켜거나 여러 개 띄워도, 화면을 새로고침해도 같은 값을 읽는다.
- **잠금을 먼저 잡고 행을 넣는다**(어드바이저리 잠금, 기존 처리 잠금과 같은 방식). 부분 유일 인덱스가 한 번 더 막는다. `interrupted` 는 저장하지 않고 "building 인데 잠금이 없음" 으로 계산한다 (서버가 죽으면 잠금이 사라지므로 따로 정리할 필요가 없다).
- **CLI 세션(`source='cli'`)은 유일 인덱스 대상이 아니다**: 명령줄 대기열은 이 경로를 쓰지 않는다.

## 이슈에 없던 결정

1. **응답 계약 변경 `201 → 202`**, 응답 세션이 빈 만드는 중 세션이다. 화면과 백엔드를 **같이** 배포해야 한다.
2. **종목 저장이 실패하면 세션이 `failed` 로 남는다** (이전에는 세션이 남지 않았다). 같은 기준일로 다시 뽑으면 지워진다.
3. **가장 최근 세션이 실패·중단이면 `latest` 도 그 세션이다.** 화면은 그 세션을 열고 이유를 카드로 보여 준다. 다른 세션은 선택기로 고른다.
4. **진행 개수를 끝난 순서로 세도록 `screen.py` 에 `map_with_progress` 를 더했다.** 원래 `pool.map` 을 순서대로 돌면 앞 종목 하나가 느릴 때 뒤가 다 끝나도 숫자가 서지 않는다.
   실제 화면 확인 중 "1/8 에서 오래 멈췄다가 끝남" 으로 드러나 고쳤다. 결과는 여전히 입력 순서이고 `run_screen` 의 결과는 같다.
5. 예시 모드의 값 복사 시점 버그(세션과 종목이 다른 시점으로 복사)를 계약 테스트가 잡아 `delay` 가 값을 지연 뒤에 만들도록 고쳤다.

## 검증 결과

- `ruff check src tests` 통과, `pytest` 691 passed (테스트 DB 사용).
- **변이 검사**(원본 복원 확인): 만드는 중 목록 처리·정리 차단 / `discard_unfinished` 제거 / `UniqueViolation` 처리 제거 / `interrupted` 계산 제거 / 진행 쓰기 간격(throttle) 제거 / 단계 변경 시 쓰기 제거 / 끝난 순서 세기 → 순서대로 세기. 모두 테스트가 실패했다.
- **실제 Chrome(헤드리스, CDP)으로 화면 확인**: 실제 백엔드·PostgreSQL·`frontend/` 에 시세·수급·분석 서버만 가짜로 끼우고 시세를 종목마다 늦췄다.
  - 만드는 중 카드와 단계·`N / 전체`·막대(시세 2/8 → 3/8), 종목 수 "—", 처리 시작·정리 막힘과 이유 문구.
  - 같은 기준일 재요청 → 409 알림 "이미 2026-11-05 목록을 뽑는 중입니다." 와 같은 세션 유지.
  - 새로고침 후에도 진행 카드가 이어짐, 끝나면 카드가 사라지고 8개 종목이 채워짐. 콘솔 오류 없음.
  - **중단됨**: 만드는 중 서버를 `kill -9` 후 다시 켜면 "중단됨" 카드와 안내가 보임. **실패**: DB 에 실패 행을 직접 넣어 "실패" 카드와 이유가 보임 (오류가 나는 경로 자체는 pytest 가 확인).
  - 같은 기준일을 다시 뽑으면 실패·중단된 목록은 지워지고 새로 만들어짐 (ID 가 바뀜).
  - 예시 모드(`?mock=1`): 시세 231/2,398 → … → 수급 → 업종 → 완료의 진행이 흐르고 콘솔 오류 없음.

## 알려진 한계 (확인하지 못한 것)

- **시세 캐시가 빈 첫 실행의 실제 진행 숫자는 이번에 측정하지 않았다.** 위 화면 확인은 가짜 시세(종목 8개)다. 약 20분은 이전 측정값(README)이다.
- 만드는 중 서버가 죽으면 목록은 완성되지 않는다 (이어받기 없음). "중단됨" 으로 알리고 같은 기준일로 다시 뽑게 한다. 시세는 캐시가 남아 있어 다시 뽑는 비용이 작다.
- 진행 숫자는 2초 간격으로 DB 에 적고 화면도 2초마다 읽으므로 최대 약 4초 늦다.
- 브라우저 자동 테스트는 아직 없다. 이번 화면 확인은 일회성 스크립트이고 저장소에 넣지 않았다 (#58).
- 개발 DB(`krx_screener`)에는 **손대지 않았다.** 머지 후 `python -m krx_screener.db init` 으로 v3 를 적용해야 한다 (백업 후 사용자 확인).
