# [fix] 분석 상태 조회가 한 번 끊겨도 서버가 끝낸 분석을 실패로 기록하지 않는다 (#75)

- 브랜치: fix/75-retry-status-poll (main 위)
- 작업일: 2026-11-08
- 요청: #75 ("#75 진행하세요"). 이슈가 "정하고 나서 진행" 이라고 한 값(횟수·간격)은 아래 "이슈에 없던 결정" 으로 가정하고 진행했다.

## 수행한 변경

- `AnalysisClient.snapshot()`: 연결이 끊기면(`ConnectionFailure`) 2초 간격으로 **3번까지 다시 시도**한다 (`SNAPSHOT_RETRIES`, `RETRY_WAIT_SECONDS`). 다시 시도할 때마다 경고 로그를 남긴다. 계속 끊기면 사유에 "분석은 서버에서 계속되거나 이미 끝났을 수 있습니다 (상태 조회를 3번 다시 시도했습니다)" 를 붙여 실패로 던진다.
- **다시 시도하지 않는 것**: 분석 시작(`start`, POST — 서버가 분석을 하나 더 시작해 쿼터를 한 번 더 쓸 수 있다), 서버가 답한 오류(404 "서버가 재시작됐을 수 있음", 5xx, JSON 이 아닌 응답).
- `ConnectionFailure(AnalysisError)` 를 새로 만들어 "응답을 받지 못함" 과 "서버가 오류로 답함" 을 구별한다. 기존 `except AnalysisError` 는 그대로 동작한다.
- `describe_exception()`: 연결 실패 사유에 예외의 속 종류를 남긴다. 예: `ConnectionError (ProtocolError → ConnectionResetError)`. 예외 **글**(주소 등)은 남기지 않고 종류 이름만 남긴다 (기존 "비밀 주소를 흘리지 않는다" 테스트 유지). 이전 사유는 `ConnectionError` 한 단어였다.
- `AnalysisClient(sleep=...)` 를 주입할 수 있게 했다 (테스트가 실제로 기다리지 않게).
- 웹(`processing.py`)과 명령줄(`cli.py`)이 같은 `run_one` → `snapshot` 을 써서 **한 곳의 수정으로 둘 다** 적용된다.
- 문서: `analysis.py` 모듈 설명, `docs/backend-design.md`(실패 규칙, 13장 한계).

## 설계 결정

- 재시도는 GET 인 상태 조회에만 건다. 서버에 아무 일도 더 만들지 않는 요청이라 다시 보내도 안전하다.
- 서버가 막 닫은 연결에 요청을 보내 한 번 끊기는 경우(keep-alive 경쟁)는 새 연결로 바로 다시 보내면 풀린다. 간격을 2초로 둔 것도 그래서다. 서버가 실제로 내려간 경우는 이 몇 초로는 풀리지 않고 이전처럼 실패로 기록된다 (404 처럼 서버 재시작은 어차피 상태가 사라진다).

## 이슈에 없던 결정

1. 횟수 **3번**, 간격 **2초** (합쳐서 최대 약 6초). 이슈는 "정해야 함" 이라고만 했다. 근거는 keep-alive 로 끊기면 첫 재시도에서 풀린다는 재현 결과뿐이고, 서버가 몇 초 멈추는 경우 등은 겪어 보지 못해서 모른다. 값이 모자라면 상수 두 개를 고치면 된다.
2. 사유 문구에 "서버에서는 끝났을 수 있습니다" 를 넣었다. 이 사유는 화면과 DB(`error_message`)에 그대로 나온다. 4건 모두 서버에서 끝나 있던 실제 사례에 근거한 문구지만, 끝났다고 단정하지 않고 "있습니다" 로 썼다.

## 하지 않은 것

- **이미 실패로 기록된 건(한국전력·하림지주·서울보증보험·한일시멘트)을 구하는 일.** 서버 로그에서 등급을 읽어 채우려면 `run_id` 를 저장하지 않는다는 규칙과 서버의 로그 덮어쓰기를 정해야 한다 (서버 쪽 TradingAgents-KR#174 와 함께). 이슈 #75 의 제안 3번은 이 PR 의 범위 밖이다.
- 연결을 요청마다 새로 맺거나 폴링 간격을 줄이는 대안. 재시도가 더 일반적으로 안전하다고 보고 택하지 않았다.
- `find_running`(분석 목록 조회)과 `report_id` 의 재시도. 이슈의 증상이 아니었다.

## 검증 결과

- `ruff check src tests` 통과, `pytest` **874 passed** (새 테스트 12개: `tests/test_snapshot_retry.py`).
- 테스트가 확인하는 것: 끊긴 뒤 다음 응답을 쓴다 / 3번까지 계속 시도 / 한도를 넘으면 더 시도하지 않고 "끝났을 수 있습니다"·예외 속 이름이 든 사유로 실패 (주소 글은 없음) / 404·500·JSON 아님·딕셔너리 아님은 다시 시도하지 않음 / 분석 시작은 다시 시도하지 않음 / `run_one` 전체 흐름에서 폴링 중 한 번 끊겨도 완료로 기록되고 POST 는 한 번뿐 / 계속 끊기면 `run_id` 가 있는 실패.
- 변이 검사(원래 코드로 복원 확인): 첫 실패에서 바로 포기 → 4개 실패 · 분석 시작도 다시 시도 → 3개 실패 · 사유의 예외 속 이름 제거 → 2개 실패.
- **실제 서버로는 확인하지 못했다.** 쿼터를 쓰는 일이고, 재시도가 실제 끊김을 얼마나 줄이는지는 긴 처리를 돌려 봐야 안다 (한 분석에 폴링 약 65번, 실제 끊김은 분석의 약 3%). 이번에는 재현에서 나온 예외 모양(`ProtocolError` → `ConnectionResetError`)을 가짜 세션으로 넣어 확인했다.
- 사용 중이던 개발 DB 와 서버(8000, 8100)는 건드리지 않았다. 새 코드를 쓰려면 `krx-screener serve` 를 다시 띄워야 한다 (실행 중인 프로세스는 이전 코드를 그대로 쓴다).
