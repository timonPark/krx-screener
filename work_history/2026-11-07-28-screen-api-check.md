## 확인 방법

브라우저 자동화 도구가 이 세션에 없어서, 이 컴퓨터의 Chrome 을 **헤드리스로 띄우고 CDP(원격 디버깅 프로토콜)를 Node 내장 `WebSocket` 으로 직접 구동**했다 (외부 패키지 없음, 임시 프로필).
화면을 실제로 열어 버튼을 누르고 DOM 값을 읽고 스크린샷을 찍었다. 같은 시나리오 스크립트를 예시 모드(`?mock=1`)와 실제 API 양쪽에서 돌렸다.

- **실제 API 쪽 서버:** 진짜 백엔드(FastAPI + 진짜 PostgreSQL + 진짜 `frontend/`)에 시세·수급·분석 서버만 가짜(테스트의 `fakes`)로 바꿔 끼웠다.
  분석 서버를 가짜로 쓴 이유는 진짜 분석이 종목당 약 5분·쿼터를 쓰기 때문이다. **개발 DB(실제 세션 116개 있음)와 테스트 DB 는 건드리지 않고** 이 확인 전용 DB(`krx_screener_e2e`)를 새로 만들어 썼다.
  가짜 분석 서버는 제어 파일로 실패·서버 꺼짐·DB 장애를 흉내 낸다.
- 확인 스크립트와 가짜 서버는 저장소에 넣지 않았다 (임시 작업물, scratchpad). 다시 필요하면 `tests/fakes.py` 위에 얹어 같은 방식으로 만들 수 있다.

주: 예시 모드에서 이중 제출로 만든 409 는 두 번째 동작이 실패한 직후 **첫 번째 동작이 성공하면서** 오류를 지운다 (성공한 새 동작이 이전 오류를 지우는 것은 의도한 동작).
실제 사용자는 처리 중에 버튼이 막혀 있어 이중 제출을 못 한다. 같은 코드 경로(`withBusy` 의 동작 출처 오류)는 실제 API 에서 위 표대로 확인했다.

| 상황 | 화면에 보인 메시지 |
|---|---|
| 처리 시작 → 다른 곳이 먼저 처리 중 (409) | 이미 처리 중입니다. |
| 처리 시작 → 분석 서버(TradingAgents-KR) 꺼짐 (503) | TradingAgents-KR 서버에 연결하지 못했습니다 (http://127.0.0.1:8000): ConnectionError |
| 새 목록 → 거래일이 아닌 기준일 (422) | 기준일 2026-11-08 은 거래일이 아니거나 시세가 아직 없습니다. 가까운 이전 거래일: 2026-11-05 |
| 조회 갱신 → DB 꺼짐 (503) | PostgreSQL 에 연결하지 못했습니다 (127.0.0.1:5433/…). 서버가 켜져 있는지 확인하세요. — DB 가 돌아와 갱신이 성공하면 사라짐 |
| 처리 시작 → 백엔드 프로세스 종료 (연결 실패) | 서버에 연결하지 못했습니다. 백엔드가 켜져 있는지 확인하세요. (화면 자체의 메시지) |
| 문제가 풀린 뒤 다시 눌러 성공 | 오류 알림이 사라지고 처리가 시작됨 |

## 발견한 결함 (고침)

**동작 오류가 20ms 만 보이고 사라졌다.** `withBusy` 는 동작이 실패하면 `showError(err)` 로 오류를 띄운 뒤 곧바로 `refresh()` 를 부르는데, `refresh()` 가 성공하면 `showError(null)` 로 오류를 지웠다.
실제 서버에서 `MutationObserver` 로 오류 알림이 몇 ms 보이는지 쟀다:

| 상황 | 수정 전 | 수정 뒤 |
|---|---|---|
| 처리 시작 → 409 (다른 곳이 먼저 처리 중) | 19ms | 계속 보임 (관찰 3초 끝까지) |
| 처리 시작 → 503 (분석 서버 꺼짐) | 23ms | 계속 보임 |
| 새 목록 → 422 (거래일이 아닌 기준일) | 25ms | 계속 보임 |
| 조회 갱신 → 503 (DB 꺼짐) | 계속 보임 (조회가 실패하니 지워지지 않음) | 계속 보임 |

화면 한 프레임이 약 16ms 라 사용자는 메시지를 읽을 수 없었다. 이슈가 정확히 확인하라고 한 "409 안내"와 "연결 실패·서버 오류 메시지가 한국어로 보이는가"가 실제로는 보이지 않았다.
(코드를 읽다가 의심했고, 브라우저에서 재현해 측정한 뒤 고쳤다. 예시 모드도 같은 코드라 같은 결함이었다.)

수정: 오류 알림이 출처(`'action'` 동작 / `'refresh'` 조회)를 기억한다 (`notice.js`). 조회가 성공하면 조회 출처 오류만 지우고, 동작 오류는 다음 동작이 성공하거나 다른 세션을 고를 때 지운다.

## 확인 중에 있었던 내 실수 (결함이 아님, 기록만)

- 가짜 분석 서버가 종목별 폴링 횟수를 실행마다 초기화하지 않아서, 이미 처리한 종목이 즉시 끝나 "다른 곳이 처리 중" 상황이 만들어지지 않았다 → 초기화하도록 고쳐 다시 돌렸다.
- 시나리오 스크립트가 (예시 모드에서) 이미 처리된 구간으로 이중 제출을 하거나, 앞 처리 뒤 화면이 갱신되기 전에 버튼을 눌러 막힌 버튼을 눌렀다 → 스크립트를 고쳤다.
- 스크립트 변수명 `path` 가 zsh 의 `PATH` 와 연결되어 명령을 못 찾는 일이 있었다 (이전 작업) — 이번에는 쓰지 않았다.

## 고치지 않은 차이 (후속 작업 제안)

**필터 문구가 고정 글자다.** `frontend/index.html` 의 "20일 평균 거래대금 10억↑ · 종가 > 20일선 · 종가 > 60일선" 은 지금 `config.yaml` 과 **같아서 맞다**.
하지만 설정을 바꾸면 새 세션·옛 세션 모두 틀린 조건을 보여주고, 세션이 목록을 뽑을 때 쓴 조건을 저장하지 않아서(스키마에 열이 없다) 백엔드가 "이 세션의 조건"을 내려줄 수도 없다
(지금 설정을 내려주면 옛 세션에는 틀린 값이 된다). 제외 조건·수급 방식도 같은 문제다. 이 수정은 스키마 변경(새 버전)과 응답 모델 변경이 필요해서 이 확인 작업에서 하지 않았다.
이슈로 남기려 했으나 이슈 생성이 이번 세션에서 허용되지 않아, 초안을 PR 본문에 적었다 (사용자가 만들지 정해 주세요).

## 알려진 한계

- 화면의 DOM 동작은 저장소 안의 자동 테스트로는 `notice.js` 의 규칙(Node 로 직접)과 `mock.js` 의 모양까지만 지킨다. `app.js` 가 그 규칙을 제대로 연결했는지는 이번 브라우저 확인으로 봤고,
  자동 회귀 테스트는 문자열 확인(`createNotice`, `clearIfFromRefresh`, `showError(err, 'action')`)뿐이다. 브라우저 자동 테스트(Chrome 필요)를 저장소에 넣을지는 정하지 않았다.
- 실제 분석 서버(TradingAgents-KR)로 처리하는 화면은 확인하지 않았다 (쿼터). 가짜 분석 서버로 화면의 처리 흐름을 확인했고, 실제 서버와의 접점은 #17~#22 에서 따로 확인했다.
- 갱신 주기가 10초라 짧은 구간(가짜 서버 기준 몇 초)은 끝나야 화면이 바뀐다. 종목당 약 5분인 실제 분석에서는 문제가 아니다 (설계 그대로).
