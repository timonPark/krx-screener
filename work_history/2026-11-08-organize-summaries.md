# [feat] 정리할 때 업종(테마)별 해석과 종합 평가를 DB 에 저장한다

- 브랜치: feat/organize-summaries (main 위)
- 작업일: 2026-11-08
- 요청: "정리 기능에서 추가 기능이 있으면 하는데요 1. 테마에 대한 해석 (수치를 기반으로) 2. 현재 한국 주식 종합적인 평가 — 위 내용을 DB에 넣을 수 있도록 해주세요". 이슈 번호 없이 요청으로 시작했다 (이슈·PR 은 사용자에게 묻고 만든다).
- 설계 선택 4가지는 사용자에게 물어 **모두 권장안**으로 정했다 (아래 "정한 것").

## 정한 것 (사용자 결정, 2026-11-08)

1. **테마 = 네이버 업종.** 스크리너가 저장하는 건 업종뿐이고 투자 테마 이름(예: HBM)은 저장하지 않는다.
2. **해석·평가 문장은 수치 계산 + 문장 틀.** 모델을 쓰지 않는다 (쿼터 0, 같은 데이터면 같은 문장).
3. **종합 평가의 범위는 후보 + 전종목 수치.**
4. **DB 저장만.** 새 테이블 추가 = 스키마 v5. API 응답·화면은 바꾸지 않는다.

## 수행한 변경

- `src/krx_screener/summary.py`(새): `summarize(items, as_of, universe_stats)` → 업종별 `ThemeSummary` 목록과 `MarketSummary`. 순수 계산이라 DB 없이 검증한다.
  순위에 들어가는 종목(끝났고 점수가 있는 종목)만 센다. 업종마다 후보 수·평균 평가점수·등급 분포·수급 상태 분포·평균 RSI·외국인/기관 5일 순매수 합계를 구해 정해진 문장 틀에 채운다.
- `src/krx_screener/db.py`: 마이그레이션 **v5** — `sessions.universe_stats`(jsonb), `session_theme_summaries`(세션·업종별 한 줄), `session_market_summaries`(세션당 한 줄). 세션을 지우면 같이 지워진다 (`ON DELETE CASCADE`).
- `src/krx_screener/repository.py`: `organize()` 가 순위를 매긴 같은 트랜잭션에서 요약을 만들어 저장한다 (이전 것은 지우고 새로 넣는다). `finish_build()` 가 전종목 수치를 받아 세션에 저장한다.
- `src/krx_screener/listing.py`·`session_build.py`: `build_items()` 가 `(종목들, 전종목 수치)` 를 돌려주고, 세션을 완성할 때 함께 저장한다. 전종목 수치는 `run_screen()` 이 이미 세던 개수(`evaluated`, `fail_each`, `candidates` 등)에서 뽑는다.
- 테스트: `tests/test_summary.py`(새, 13개), `tests/test_organize_summary_api.py`(새, 11개). 스키마 버전이 오른 것에 맞춰 `tests/test_db.py`·`tests/test_api_base.py` 갱신 (v5 와 새 테이블·컬럼, health 의 `schema_version`, "옛 스키마" 흉내가 v5 도 되돌리도록).
- 문서: `GLOSSARY.md`(테마 해석·종합 평가·전종목 수치), `docs/backend-design.md` 8장.

## 설계 결정

- **전종목 수치는 목록을 만들 때 저장한다.** 정리 때 전종목 시세를 다시 읽을 수 없다 (종목마다 외부 조회, 캐시가 없으면 수천 번). 시세를 다 읽는 `run_screen()` 의 개수를 그 순간 저장하는 것이 유일하게 싸다.
- **문장의 기준 두 가지는 임의의 값이다.** 업종 평균이 후보 전체 평균과 0.2(= 에이전트 평균의 두 단계) 이상 다르면 높다·낮다고 쓰고(`COMPARE_GAP`), 업종의 후보가 3개 미만이면 "참고만 하세요"(`MIN_THEME_SIZE`)를 붙인다. 백테스트로 정한 값이 아니다.
- **요약은 순위와 같은 트랜잭션이다.** 요약이 실패하면 순위·정리 시각도 이전 그대로다 (테스트로 확인, 요약 저장을 트랜잭션 밖으로 옮기면 테스트가 실패한다).
- **문장은 추천·전망을 하지 않는다.** GLOSSARY 의 "후보는 추천 종목이 아니고 순위는 투자 판단이 아니다" 를 따른다. 종합 평가에는 "후보는 시장 전체를 대표하지 않는다" 가 늘 붙고, 테스트가 추천·전망 단어가 없음을 검사한다.
- 요약 테이블의 등급·수급 분포는 영어 내부값으로 저장하고(`Hold`, `strong` …), 한국어는 문장에만 쓴다 (i18n 경계).

## 이슈에 없던 결정

1. **목록을 만들 때 전종목 수치를 저장하는 변경을 같이 넣었다** (`build_items` 반환 모양, `sessions.universe_stats`). 사용자가 고른 "후보 + 전종목 수치"가 안전하게 동작하는 데 꼭 필요하다.
2. 종합 평가에 **지수 등락률 같은 시장 지수는 넣지 않았다.** 스크리너는 지수를 조회하지 않는다 (새 외부 조회가 필요하고, 요청 밖이다). 넣는 것은 별도 이슈로 제안한다.
3. 이미 만든 세션에는 전종목 수치가 없다. **다시 채우지 않았다** (그 날의 전종목 시세를 다시 읽어야 한다). 그런 세션의 종합 평가는 "전종목 수치가 저장되어 있지 않다"고 말한다.

## 하지 않은 것 / 다음 작업 핸드오프

- **사용자 DB 에 v5 를 적용하지 않았다.** 이 브랜치가 머지된 뒤 `python -m krx_screener.db init` 을 실행해야 새 테이블이 생긴다. 적용하기 전에는 새 코드로 정리하면 `503 DB 스키마가 최신이 아닙니다` 이다 (`UndefinedTable` 처리).
- 요약을 읽는 API·화면은 만들지 않았다 (요청 범위가 DB 저장만). 필요하면 세션 조회 응답에 넣는 것을 별도 이슈로.
- 이미 정리한 세션(예: 2026-11-05)의 요약은 **정리를 다시 실행해야** 만들어진다. 그 세션은 전종목 수치가 없으므로, 전종목 수치까지 보려면 같은 기준일 목록을 새로 만들어야 한다.
- 실행 중인 서버(`krx-screener serve`)는 재시작해야 새 코드를 쓴다.
