# [feat] 구간 처리는 실패한 종목을 빼고, 실패한 종목은 버튼으로 다시 처리한다 (#77)

- 브랜치: feat/77-exclude-failed-retry-button (main 위)
- 작업일: 2026-11-08
- 요청: #77 ("#77 진행하세요"). 이슈에 "정해야 함" 으로 남은 4가지는 사용자에게 물어 **모두 권장안**으로 정했다 (아래 "정한 것").

## 정한 것 (사용자 결정, 2026-11-08)

1. 버튼은 **세션의 실패한 종목 전체를 한 번에** 다시 보낸다 (행마다 버튼 없음).
2. **영숫자 코드**(서버가 숫자 6자리만 받음)는 버튼 대상과 전송에서 **뺀다**. 뺀 개수는 힌트로 알린다.
3. 서버 API 는 **새 경로** `POST /api/sessions/{id}/process-failed`. 기존 `/process` 의 오프셋·개수 의미는 그대로다.
4. 쿼터는 **확인창**으로 알린다 ("N개 · 약 M분 · 분석 쿼터 최대 N번").

## 수행한 변경

- `routes_sessions.py`: 구간 처리(`/process`)가 **대기(와 처리하던 서버가 죽어 `running` 으로 남은) 종목만** 보낸다. 끝난 종목과 실패한 종목은 보내지 않는다. 구간 안에 보낼 것이 없으면 `200 {"started": false, "queued": 0}`.
- `routes_sessions.py`: 새 `POST /{id}/process-failed`. 구간 없이 세션 전체의 `failed` 종목 중 `server_accepts(code)`(숫자 6자리)인 것을 순번 순서로 보낸다. 시작 절차(`_start_processing`: 만드는 중 409 → 세션 잠금 409 → 서버 확인 503 → 응답 모양)는 구간 처리와 **같은 함수**를 써서 두 경로가 어긋나지 않게 했다.
- 화면: 처리 폼 아래 `실패한 종목 다시 처리 (N개)` 버튼과 힌트, 누르면 `window.confirm`. 구간 처리의 대상·예상 시간·힌트가 실패한 종목을 세지 않는다 (`끝난 M개·실패한 K개는 건너뜀`, 실패만 남은 구간은 "모두 끝났거나 실패했습니다"). 실패한 행의 보조 문구는 `… · 아래 '실패한 종목 다시 처리' 로 재시도` (영숫자 코드는 사유만).
- `frontend/src/retry.ts`(새): `serverAccepts`, `retryPlan`. `api.ts`·`types.ts`·`mock.ts` 에 `processFailed` 를 더했고 예시 모드가 백엔드처럼 동작한다.
- 테스트: `tests/test_process_failed_api.py`(새, 16개), 실패 재시도에 기대던 기존 테스트 16곳을 새 경로로 바꿨다, 브라우저 시나리오·계약 테스트 보강.
- 문서: `docs/backend-design.md`, `docs/frontend-spec.md`, `frontend/README.md`, `README.md`, `GLOSSARY.md`.

## 설계 결정

- 응답에 "뺀 영숫자 코드 수" 같은 필드를 더하지 않았다. 화면이 조회 결과(`items`)로 직접 센다. (API 필드를 늘리지 않으려는 선택.)
- 영숫자 코드 판별을 화면(`retry.ts`)에도 두었다. 백엔드 `analysis.server_accepts` 와 같은 규칙이고 `tests/test_frontend_contract.py` 가 같은 코드들로 두 구현을 대조한다.
- 다시 처리하는 동안에도 세션 잠금을 쥔다: 그 사이 구간 처리가 들어오면 409 (테스트로 확인).

## 이슈에 없던 결정

1. **`running` 으로 남은 종목은 구간 처리가 계속 보낸다** (이슈 5번). 실패가 아니라 "끝나지 않은 것" 이고, 서버가 죽어 남은 종목을 다시 처리할 수 있어야 해서 기존 동작(`test_a_stock_left_running_by_a_crash…`)을 유지했다.
2. **"남은 N개" 계산은 바꾸지 않았다** (이슈 6번). 정리의 남은 개수는 이미 `대기 + 처리 중` 만 세고 실패는 세지 않는다 (코드와 기존 테스트로 확인).
3. 확인창은 브라우저 기본 `window.confirm` 이다. 화면 안의 별도 확인 UI 는 만들지 않았다. 쿼터는 "최대 N번" 이라고 적었다: 서버에서 아직 도는 분석을 이어받으면(#70) 더 적게 쓸 수 있고, #75 처럼 서버에서는 끝났는데 실패로 기록된 건은 한 번 더 쓴다.
4. 목록을 만드는 중인 세션에 `process-failed` 는 구간 처리와 같은 문구의 409 다.
5. 브라우저 테스트가 확인창을 다루도록 `tests/browser/cdp.ts` 에 대화상자 처리(문구 기록, 확인/취소)를 더했다.

## 하지 않은 것

- 행마다 재시도 버튼 (정한 대로 전체 버튼만).
- **명령줄 `analyze` 가 실패 종목을 어떻게 다루는지는 확인하지도 바꾸지도 않았다** (이슈도 웹 처리 경로만 대상이라고 했다). 명령줄은 웹 처리 경로를 거치지 않는다.
- #75 의 "이미 실패로 기록된 건 구하기" (TradingAgents-KR#174 와 함께 다룬다). 이 PR 로 그런 건을 다시 돌릴 수는 있지만 쿼터를 한 번 더 쓴다.
- 실제 서버로 다시 처리를 돌려 보지 않았다 (쿼터).

## 검증 결과

- 테스트를 먼저 썼다: 새 `test_process_failed_api.py` 는 구현 전에 15개 실패(1개는 기존 동작 유지 확인이라 통과)였다.
- `ruff check src tests` 통과, `pytest` **893 passed** (실제 Chrome 브라우저 테스트 7개 포함), `npm run typecheck`·`npm run lint` 통과.
- 변이 검사(복원 확인): 구간 처리가 실패 종목도 보내도록 되돌리면 3개 실패, 다시 처리가 영숫자 코드도 보내도록 하면 2개 실패.
- 브라우저 시나리오가 실제 Chrome 으로 확인한 것: 실패 1개일 때 버튼 글자·힌트, 실패만 든 구간의 처리 버튼이 막히고 힌트와 예상 시간이 `0분`, 확인창 문구, 취소하면 아무것도 시작하지 않고(실패 1 그대로) 확인하면 실패한 종목만 다시 돌아 완료, 다시 정리 전 순위 낡음 표시.
- 발견한 차이: Python 의 `\d` 는 전각 숫자(`００５９３０`)도 숫자로 읽지만 화면의 `/^\d{6}$/` 는 읽지 않는다. 실제 종목코드는 ASCII 라서 영향은 없다고 보고 계약 테스트에서 이 입력은 뺐다 (백엔드 규칙은 바꾸지 않았다).
- **확인하지 못한 것**: 실제 TradingAgents-KR 서버로 다시 처리 (쿼터), 화면의 시각적 모양(스크린샷은 보지 않았다 — 버튼 줄의 CSS 는 `.retry-row` 한 줄이다). 개발 DB·서버(8000, 8100)는 건드리지 않았다. 새 화면을 쓰려면 `npm run build` 후 `krx-screener serve` 를 다시 띄워야 한다.
