# [#18] 세션 단위 동시 처리 잠금 (409, 연결이 끊기면 해제)

- 이슈: https://github.com/timonPark/krx-screener/issues/18 (에픽 #4, 스펙 #1)
- 브랜치: feat/18-session-lock (main 위)
- 작업일: 2026-11-07

## 수행한 변경

- `repository.py`: `SessionRepository.try_lock(session_id)` (기다리지 않고 잠금을 쥐려 시도) 와 `is_locked(session_id)`
  (DB 의 잠금 목록 `pg_locks` 만 보고 잠금을 건드리지 않는다) 추가. 잠금은 PostgreSQL 의 연결 단위 advisory lock 이다.
- `routes_sessions.py`:
  - `POST /api/sessions/{id}/process` 가 **구간을 읽기 전에** 잠근다. 이미 처리 중이면 `409 {"detail": "이미 처리 중입니다."}`.
  - 잠금을 쥔 자동 커밋 연결을 백그라운드 처리에 넘긴다. 처리를 시작하지 않고 끝나는 경우(200, 422, 503, 예외)에는
    요청 안에서 연결을 닫아 잠금을 푼다.
  - `GET /api/sessions/{id}` 의 `processing` 이 잠금 상태(`is_locked`)를 따른다.
- `processing.py`: `process_codes(deps, conn, ...)` 가 잠금을 쥔 연결을 받아 일하고, 끝나면 닫는다. (이전에는 자기 연결을 열었다.)
- `tests/test_session_lock.py` 신규 11개, `tests/conftest.py` 에 `hold_lock` 픽스처.
  `tests/test_session_detail_api.py` 의 "실행 중인 종목이 있으면 processing" 테스트는 잠금 기준 테스트로 대체해 지웠다.

## 설계 결정 (이슈 #18 범위 안에서 내가 정한 것)

- **잠금은 구간 계산보다 먼저**: 동시에 온 두 요청이 같은 종목을 둘 다 대기열에 올리지 못하게 한다. 그 결과 보낼 종목이 없는
  구간이라도 처리 중이면 200 이 아니라 409 다.
- **잠금 키는 세션 UUID 앞 8바이트의 64비트 정수**. 32비트 두 키로 나누면 세션끼리 겹쳐 "다른 세션은 막히지 않는다" 가 깨질
  확률이 커서 64비트 한 키를 썼다. 스키마 적용 잠금(`db._MIGRATION_LOCK`)과 겹칠 확률은 사실상 0 이다.
- **`processing` 은 종목 상태(`running`)가 아니라 잠금으로 판단**한다. 처리하던 프로세스가 죽으면 `running` 표시는 남지만 잠금은
  풀리므로, 화면이 영원히 "처리 중" 으로 보이지 않고 같은 구간을 다시 처리할 수 있다 (테스트: 죽은 뒤 남은 `running` 은 다시 처리된다).
  `counts.running` 은 그대로 남은 표시를 보여준다.
- **잠금을 쥔 연결을 요청에서 백그라운드로 넘긴다** (연결 소유권 이전). 요청과 백그라운드가 서로 다른 연결을 쓰면 잠금이 요청이
  끝날 때 풀린다.

## 검증 결과

- `pytest`: 테스트 DB 연결 시 **385 passed** (이전 374 − 1 + 12), DB 없이 **245 passed, 140 skipped**. `ruff` 통과.
- 완료 조건 대조(웹 API 경계, 진짜 Postgres):
  - 처리 중에 같은 세션을 다시 처리하면 409 ✓ (잠금을 쥔 다른 연결, 그리고 실제 처리 도중 분석 서버 호출 안에서 보낸 두 번째 요청 둘 다)
  - 다른 세션은 막히지 않는다 ✓
  - 처리 연결이 끊기면 잠금이 풀려 다시 처리할 수 있다 ✓ (연결을 닫은 뒤 202)
  - 조회의 `processing` 이 잠금 상태를 반영한다 ✓
- 잠금이 남지 않는 경로: 정상 종료, 모든 종목 실패, 서버 꺼짐(503), 오프셋 초과(422), 보낼 것 없음(200) ✓

## 알려진 한계

- 잠금은 **연결 하나가 쥔다**. 처리하는 내내 DB 연결 한 개가 열려 있다 (처리 도중 `max_connections` 여유가 필요).
- 서버(웹 프로세스)가 죽으면 연결이 끊겨 잠금은 풀리지만, 이미 TradingAgents-KR 로 보낸 분석은 서버에서 계속 돌 수 있다
  (취소 API 없음). 같은 종목을 바로 다시 보내면 쿼터를 한 번 더 쓴다.
- 이 이슈에서는 정리(#24) 쪽 게이팅(처리 중이면 정리 거절)을 만들지 않았다. `is_locked` 를 그대로 쓰면 된다.
