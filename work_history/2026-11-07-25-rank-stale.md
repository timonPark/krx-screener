## 설계 결정 (이슈 #25 범위 안에서 내가 정한 것)

이슈 본문은 "정리 뒤에 어떤 종목이 다시 분석되면 true" 다. 문자 그대로(정리 뒤에 `analyzed_at` 이 바뀐 종목이 있으면 true) 구현하면 **순위가 달라질 수 없는 재시도**에서도
"정리 이후 다시 분석된 종목이 있습니다. 최신 순위를 보려면 정리를 다시 실행하세요"(화면 문구)가 떠서 사용자를 오도한다. 실패했던 종목을 다시 처리했는데 또 실패하면
(`mark_failed` 가 `analyzed_at` 을 갱신한다) 그 종목은 정리 때도 지금도 비교에서 빠져 있어서 다시 정리해도 순위가 같다. 그래서 정의를 이렇게 정했다:

```text
정리 시각 뒤에 분석된 종목 중
  정리할 때 순위가 있던 종목          (점수가 바뀌었거나, 실패해서 비교에서 빠져야 한다)
  또는 지금 점수와 함께 끝난 종목      (순위에 새로 들어와야 한다)
이 하나라도 있으면 낡음.
```

- 낡음이 아닌 경우: 실패했던 종목이 또 실패, 점수가 없던 종목이 또 점수 없음, 점수가 없던 종목이 실패. (모두 테스트로 고정)
- 이슈의 완료 조건 세 가지(정리 전 false·정리 직후 false·정리 후 재분석하면 true·다시 정리하면 false)는 그대로 만족한다. 문자 그대로의 정의와 다른 점은 위 "낡음이 아닌 경우"뿐이다.
- 낡음은 저장하지 않고 **조회할 때마다 계산**한다 (`ranked_at` 과 종목의 `analyzed_at`·`rank`·`state`·`score` 로 정해진다). 그래서 정리를 다시 실행하면 별도 처리 없이 false 로 돌아온다
  (`organize` 가 `ranked_at` 을 갱신하고 순위를 새로 매긴다).
- 비교는 `analyzed_at > ranked_at` (엄격). `ranked_at` 은 정리 트랜잭션의 시작 시각이고, 정리는 처리 잠금(#18)을 쥐어서 그 사이에 분석이 끝나는 종목이 없다.

## 검증 결과

- `pytest`: 테스트 DB 연결 시 **552 passed** (이전 541), `ruff` 통과.
- 변이 검사 6종 모두 테스트가 잡았다(확인 후 원복): 정리 시각 조건 제거, 순위 영향 조건 전체 제거(실패→실패도 낡음), 순위 있던 종목 조건만 제거,
  새로 순위에 들 종목 조건만 제거, 다른 세션까지 봄, 조회가 항상 false.
- 완료 조건 대조(웹 API 경계, 진짜 Postgres): 정리 전 false · 정리 직후 false ✓ / 정리 뒤에 실패했던 종목을 다시 처리해 성공하면 true, 다시 정리하면 false ✓
  (그 종목이 순위에 들어온 것도 확인).
- 이 API 로는 끝난(`done`) 종목을 다시 보낼 수 없다 (#17). 그래서 "순위 있던 종목이 재분석됨" 은 저장소 호출(`mark_done`·`mark_failed`)로 재현했다 — 재분석을 시작하는
  경로(예: `--redo` 같은 것)는 아직 없다.

## 알려진 한계

- 재분석을 시작하는 API 가 아직 없어서, 지금 실제로 낡음이 켜지는 경로는 "정리 때 실패였던 종목을 다시 처리해 성공/실패"뿐이다 (이때 성공만 낡음). 순위가 있던 종목을 다시 분석하는 기능이 생기면
  같은 규칙이 그대로 적용된다 (테스트가 그 경우를 저장소 호출로 이미 확인한다).
- 시각 비교라서 시계가 거꾸로 가는 환경(같은 DB 를 서로 다른 시계의 서버가 쓰는 경우)에서는 어긋날 수 있다. `now()` 는 DB 서버의 시계라 한 DB 를 쓰는 한 일관된다.
