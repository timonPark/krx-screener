## 설계 결정 (이슈 #17 범위 안에서 내가 정한 것)

- **구간은 순번 기준**: 순번이 `offset+1 ~ offset+count` 인 종목. 개수가 목록을 넘어가면 마지막 종목까지만.
- **구간 안에서 `done` 이 아닌 종목을 모두 보낸다** — `pending` 뿐 아니라 `failed`(재시도)와 처리 중에 프로세스가 죽어 남은 `running`
  도 포함한다. 그래서 실패한 종목은 같은 구간을 다시 호출하면 재시도된다 (#19 의 기본 동작이 이미 들어 있다).
- **응답은 두 가지**: 보낼 종목이 있으면 `202 {"started": true, "queued": N}`, 구간이 모두 끝나 있으면 아무것도 보내지 않고
  `200 {"started": false, "queued": 0}`.
- **시작 전에 서버 상태를 확인**한다(`check_health`). 서버가 꺼져 있으면 아무 종목도 `running` 으로 바꾸지 않고 한국어 503.
- **백그라운드 처리는 자동 커밋 연결을 쓴다.** 종목 하나가 끝날 때마다 바로 보여야 조회가 진행 상황을 볼 수 있다 (테스트로 확인:
  분석 중에 다른 연결로 읽으면 현재 종목은 `running`, 앞 종목은 이미 `done`).
- **한 종목의 예상하지 못한 오류도 나머지를 멈추지 않는다.** 그 종목을 `failed`("처리 중 오류가 났습니다 (RuntimeError)")로 표시하고
  다음으로 간다. 세션이 도중에 지워지면 조용히 멈춘다.
- 이 이슈에서는 서버가 알려준 **최종 등급만** 저장한다. 에이전트별 등급(#21)과 점수(#22)는 비워 둔다 (`score` NULL, 에이전트 수 0).
- 서버 상태 문제는 503, 입력 문제는 422, 없는 세션은 404 — 모두 `{"detail": 한국어}`.

## 검증 결과

- `pytest`: 테스트 DB 연결 시 **374 passed**, DB 없이 **245 passed, 129 skipped**. `ruff` 통과.
- 완료 조건 대조(웹 API 경계, 가짜 분석 서버):
  - 구간 밖 종목은 건드리지 않는다 ✓ (offset 1, count 2 → 순번 2·3 만, 나머지는 `pending`)
  - 끝난 종목은 다시 보내지 않는다 ✓ (완료된 종목의 등급이 그대로, 서버 호출 기록에도 없음)
  - 종목은 순번 순서로 한 개씩 보내진다 ✓ (호출 기록의 순서)
  - 잘못된 입력은 한국어 `detail` 로 거절된다 ✓ (오프셋 음수·개수 0·숫자 아님·없음, 오프셋이 목록 이상)
- **실제 서버와의 접점(쿼터를 쓰지 않고 확인)**: `check_health` 가 실제 서버에서 정상. 일부러 잘못된 종목코드(`ABC`)를 `POST /api/runs`
  에 보내면 서버가 분석을 시작하기 전에 422 로 거절하고, 거절 사유에 `ticker` 만 나온다 → `trade_date`·`effort` 필드는 서버가 인정한다.
  서버의 실행 기록에 새 실행이 생기지 않았음을 확인했다.
- **실제 분석은 이 API 로 돌려 보지 않았다.** 종목당 약 5분·Max 플랜 쿼터를 쓰는 일이라서, 가짜 서버와 위 접점 확인까지만 했다.

## 알려진 한계

- **처리 도중에 프로세스가 죽으면 그 종목이 `running` 으로 남는다.** 같은 구간을 다시 호출하면 `done` 이 아니라서 다시 보내지만,
  그때까지 조회의 `processing` 이 true 로 남는다. 세션 잠금(#18)이 생기면 `processing` 을 잠금 상태로 바꿔 해결한다.
- **같은 세션을 동시에 두 번 호출하면 같은 종목이 두 번 분석될 수 있다.** 이것을 막는 것이 #18 이다.
- 서버에는 취소 기능이 없어서 시작한 분석은 멈출 수 없다.
- 서버가 알려준 등급 문자열을 읽지 못하면 `REVIEW` 로 저장한다 (`analysis.run_one` 의 기존 동작).
