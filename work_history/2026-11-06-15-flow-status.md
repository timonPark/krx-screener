## 설계 결정 (이슈 #15 범위 안에서 내가 정한 것)

- **수급은 표시만 하고 종목을 거르지 않는다.** 설정의 `flow.mode: filter` 도 **API 는 따르지 않는다** (스펙: "수급은 표시만
  한다"). CLI(`analyze` 가 아니라 기존 `run`)의 `filter` 모드는 그대로지만 API 경로에서는 늘 표시만 한다. 테스트로 고정했다.
- **창 길이는 설정(`flow.window_days`, 기본 5)을 따른다.** DB 칼럼 이름이 `foreign_net_5d` 라서 5가 아닌 값을 쓰면 이름과 내용이
  어긋난다. 기본값을 바꿀 일이 없어서 그대로 두고 여기에 적어 둔다.
- **읽지 못한 종목은 `unconfirmed` 이고 합계는 빈 값(NULL)** 이다 ("수급 0" 이 아님). 사유(조회 실패 / 데이터 없음 / 기준일 행
  없음 등)는 저장하지 않는다 — 스키마에 자리가 없고 스펙에도 없다.
- 수급 가짜는 모르는 종목에 빈 목록을 돌려준다 (실제 네이버와 같다). 그래서 #14 의 가짜 세계에서는 그 종목들이 `unconfirmed` 다.

## 검증 결과

- `pytest`: 테스트 DB 연결 시 **301 passed**, DB 없이 **219 passed, 82 skipped**. `ruff` 통과.
- **실제 네이버 수급 대조**: 2026-11-05 목록 116개에 실제 조회를 붙여 4.6초. 양호 34 · 부분 72 · 약함 10 · 미확인 0.
  어제 `candidates.csv` 에 저장한 수급과 겹치는 100개 종목은 **100개 모두 같은 값**(상태·외국인 합계·기관 합계).
- 웹 API 경계 테스트: 부호에 따른 상태 3종 + 합계 값 / 조회 실패·모르는 종목은 `unconfirmed`+빈 합계이고 목록에 남음 /
  약함 종목도 `filter` 설정에서 빠지지 않음 / 창 길이가 설정을 따름(3일 → 300·150) / 수급 제공 범위(10거래일) 밖 기준일은
  전부 미확인 / 제외·탈락한 종목은 조회하지 않음(호출 기록으로 확인) / 수급 서버가 전부 죽어도 요청은 성공.

## 알려진 한계

- 수급은 네이버 비공식 주소라 바뀌면 전부 `unconfirmed` 로 보인다 (목록은 그대로 만들어진다).
- 기준일이 최근 10거래일보다 오래되면 수급은 전부 미확인이다 (네이버가 최근 10거래일만 준다).
- 종목마다 한 번씩 외부 호출이라 목록이 길수록 느려진다 (116개에서 약 4~5초, 8개 동시).
