# [feat] 평가점수를 100 을 곱한 정수로 화면에 표시한다 (#76)

- 브랜치: feat/76-score-times-100 (main 위)
- 작업일: 2026-11-08
- 요청: #76 ("#76 진행하세요"). 이슈의 결정(표시만 `round(score × 100)`, 음수 그대로, 서버·DB 불변)을 그대로 따랐다.

## 수행한 변경

- `frontend/src/app.ts` 의 `fmtScore`: 소수 둘째 자리(`+0.40`) 대신 100 을 곱한 정수(`+40`)로 보인다. 부호(+/−)는 붙이고 0 은 부호가 없다.
- 점수 막대(`scoreCell`)는 저장값 기준(±2 → 최대 30px)이라 모양이 같다. 바꾸지 않았다.
- 서버·DB·API 필드·정렬·순위는 바꾸지 않았다 (정렬과 순위는 원래 값으로 한다).
- 테스트: `tests/browser/scenarios.ts` 의 `processAndOrganize` 가 화면에 보이는 점수 글을 사실로 남기고, `tests/test_browser_screen.py` 가 대조한다.
- 문서: `docs/frontend-spec.md`(표시 규칙), `GLOSSARY.md`(평가점수), `README.md`·`docs/backend-design.md`(몰림 설명에 표시값 병기).

## 설계 결정

- 반올림은 **부호를 뗀 값**으로 한다 (`Math.round(|s| × 100)`). `Math.round(-0.5)` 가 `-0` 이 되거나 음수 쪽이 양수 쪽과 다르게 반올림되는 것을 피한다. 반올림 결과가 0 이면 부호를 붙이지 않는다.
- `frontend/src/mock.ts` 는 같은 `fmtScore` 를 거치므로 바꾸지 않았다 (예시 점수 그대로, 표시만 바뀐다).

## 이슈에 없던 결정

- 없음. 다만 이슈의 "표시만 같고 순위는 다를 수 있다" 는 서로 다른 값이 같은 정수로 보일 수 있다는 뜻이고, 이 PR 은 그것을 막지 않는다 (순위는 원래 값 기준).

## 검증 결과

- 테스트를 먼저 썼다: 기대값 `+60 −80 +20 — +40 0 +60 −40` 으로 고정하자 구현 전에는 실패했다 (그때 화면은 `+0.60 −0.80 +0.20 — +0.40 0.00 +0.60 −0.40`).
- 구현 뒤 `tests/test_browser_screen.py` 7개 통과 (실제 Chrome), `ruff check src tests` 통과, `pytest` **874 passed**, `npm run typecheck`·`npm run lint` 통과.
- 빌드한 `dist/app.js` 의 `fmtScore` 를 Node 로 직접 불러 가장자리 값을 확인했다: `0.4→+40`, `−0.3→−30`, `0→0`, `±0.004→0`, `±0.005→±1`, `±2→±200`, `2/3→+67`, `null→''`.
- 한계: `fmtScore` 자체의 단위 테스트는 없다 (화면 테스트가 8종목의 대표값만 본다). 위 가장자리 값은 일회성 확인이다. 점수는 최대 10개 에이전트 평균이라 실제로는 0.1 단위에 가까워 ±0.005 경계는 거의 나오지 않는다.
- 이 PR 은 개발 DB·서버(8000, 8100)를 건드리지 않았다. 새 화면을 쓰려면 `krx-screener serve` 를 다시 띄워야 한다 (`frontend/dist` 를 다시 빌드한 뒤).
