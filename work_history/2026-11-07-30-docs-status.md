## 이미 되어 있던 것

설계 문서(`docs/backend-design.md`), 화면 명세(`docs/frontend-spec.md`), ADR 0001, API 테스트 방법(`docs/api-testing.md`)은 이전 작업(#1~#28)에서 이미 저장소에 커밋되어 있다.
이 이슈에서 남은 일은 **서로 링크하고, 낡은 서술을 구현 상태에 맞게 고치는 것**이었다.

## 수행한 변경

- `README.md` **다시 씀**: 웹 화면 중심으로 재구성했다 — 기능 표(세션 웹 흐름 추가), 준비(venv·DB·환경변수·`db init`), 웹 화면(`serve`, 4단계 설명, 로컬 전용), 명령줄(`run`·`analyze`·`list`), `analyze` 동작 설명을 목록으로,
  **문서 목차**(모든 문서로 가는 링크), 읽을 때 주의(평가점수·순위가 견주는 용도라는 점 추가). 상태 줄에 "실제 분석 서버로 끝까지 돌린 것은 시범 3개뿐"을 솔직히 적었다.
- `CLAUDE.md`: 요지에 웹 API·화면·평가점수를 추가하고, 설계 제약에 `run_id` 비저장·`report_id`, 에이전트별 등급이 같은 컴퓨터의 로그라는 점을 더했다. 참조 목록에 모든 문서를 넣었다.
  (SQLite 문장은 #12 에서 이미 고쳤다.)
- `docs/backend-design.md`: 상태 줄 "설계 확정(구현 전)" → "구현됨", 관련 문서 링크, 낡은 표현 정정(5장 "보고서에서 에이전트별 등급" → 분석 상태 로그, 3장 "값을 주지 않으면 가장 최근 세션" → `latest`),
  11장 "화면 (추론)" → "화면", 13장 한계 보강, **14장을 "구현 상태와 설계와의 차이"로 다시 씀**(기능 ↔ 주소 ↔ 구현 파일 표 + 설계와 달라진 결정 목록, 각각 `work_history` 기록으로 연결).
- `docs/api-testing.md`: 짝 문서 링크, 새 픽스처(`hold_lock`·`queue_db`)와 `FakeAnalysisServer` 의 새 인자, 예시의 `schema_version` 1 → 2, "명령줄과 화면" 절(CLI·화면 계약·화면 서빙 테스트).
- `docs/adr/0001-postgres-analysis-queue.md`: 관련 문서 링크. `frontend/README.md`: 화면 명세·README 링크.

## 설계 결정 (이슈 #30 범위 안에서 내가 정한 것)

- README 는 **웹 화면을 먼저, 명령줄을 나중에** 두었다 (설계가 웹 API 를 기본 인터페이스로 보므로). 명령줄 `analyze` 의 긴 설명 한 문단은 목록으로 쪼갰다 (내용은 그대로).
- README 상단에 **실제로 검증한 범위를 적었다** ("시범 3개뿐, 웹 경로는 가짜 분석 서버로 확인"). 문서가 구현보다 낙관적이면 쿼터를 쓰는 일에서 오해를 부른다.
- 14장은 이슈 번호·PR 번호 대신 **`work_history` 파일 이름**으로 연결했다 (저장소 안에서 링크가 깨지지 않는다).
- 용어집(`GLOSSARY.md`)은 #29(PR #53) 가 맡아서 이 PR 에서는 건드리지 않았다. README 가 용어집을 링크한다.

## 검증 결과

- **README 의 실행 방법을 새 환경에서 그대로 따라 해 봤다** (새 가상환경, 새 DB `krx_screener_readme`):
  - `uv venv --python 3.13 && uv pip install -e ".[dev]"` → 성공, `uvicorn` 이 의존성으로 같이 설치됨. `krx-screener --help` 에 `universe, run, analyze, list, serve` 가 나온다.
  - `docker compose up -d` 로 띄운 PostgreSQL 이 `healthy`.
  - **`db init` 을 하기 전에 `serve`** → `/api/health` 가 한국어로 `DB 스키마가 없습니다. python -m krx_screener.db init 을 실행하세요.` → `db init`(적용한 버전: 1, 2, 다시 실행하면 "이미 최신") → `serve` 의 `/api/health` 가 `schema_version: 2`.
  - `/`·`/?mock=1` 이 200 `text/html`, `/api/sessions` 가 200 JSON, 서버를 종료하면 포트가 비워짐.
  - 쿼터를 쓰지 않는 명령줄(`analyze --dry-run`, `list`)은 #12 에서 실제 후보 파일로 확인했다 (이 PR 의 문서 설명과 옵션 이름이 같다).
- 문서 링크 점검(스크립트): 마크다운 링크·백틱 속 저장소 경로·`work_history` 파일 이름이 모두 실제로 존재하고, README 에서 모든 문서(8개)에 닿는다. 설계 문서 ↔ 화면 명세 ↔ API 테스트 문서 ↔ ADR 이 서로 링크된다.
- `pytest` 테스트 DB 연결 시 655 passed (문서만 바꿨다). `ruff check src tests` 통과. (`main` 에 있던 import 정렬 위반 1건은 별도 PR #54 로 먼저 고쳐 머지했고, 이 브랜치는 그 위에서 시작했다.)

## 실제 "새 목록 뽑기" 검증 (README 의 핵심 절차를 실제 조회로)

새 DB·새 시세 캐시로 `POST /api/sessions` (기준일 2026-11-06)을 **실제 시세·수급·업종 조회로** 돌렸다 (네트워크 읽기만, 모델·쿼터 없음).

| 측정 | 값 |
|---|---|
| 캐시가 비어 있는 첫 실행 | **약 20분** (첫 시세 캐시 08:12:17 → 세션 저장 08:32:16, 시세 약 2,385개 조회) |
| 같은 기준일을 다시 뽑기 (캐시가 있음) | **5.1초** (HTTP 201) |
| 결과 | 후보 **95개**, 거래대금 큰 순 정렬, 수급 부분 56·양호 28·약함 11, 업종·기업 설명 95/95, RSI 95/95, 영숫자 코드 2개(`0126Z0`·`0088M0`) 포함 |
| 전종목 | 코스피 938 + 코스닥 1,831 = 2,769개 (제외 규칙 적용 뒤 시세를 받는 종목 약 2,400개) |

- README 의 "약 1~2분"(이전 서술)은 캐시가 있을 때의 이야기였고, 처음 실행은 훨씬 오래 걸린다. 측정한 값(20분 / 5초)으로 고쳤다. `run` 명령의 시간은 따로 재지 않았다.
- 서버 안에서 시세 조회는 종목 약 2,400개를 **8개씩 동시에** 받는다 (동시 8개이지 8종목이 아니다). 같은 기준일로 다시 뽑으면 별도의 새 세션이 생기고 내용은 같다.
- **내가 중간에 한 오판 (정정):** 캐시가 2분간 늘지 않고 서버가 시세용 주소(`fchart.stock.naver.com`)에 8개 연결을 유지하는 것을 보고 "시세 단계에서 멈췄을 수 있다"고 의심했다.
  7초 뒤 세션이 저장되며 끝났다. 마지막 종목들과 수급·업종 조회가 이어지던 구간이었고, 멈춤이 아니었다.
- **발견한 한계:** 첫 실행에서는 요청 하나가 약 20분 걸린다. 내 검증용 `curl`(제한 15분)은 응답을 못 받고 끊겼지만, **서버는 요청을 끝까지 처리해 세션을 저장했다**(DB 로 확인). 브라우저에서도 끊기면 같은 일이 생겨,
  화면에는 오류가 보이는데 세션은 만들어질 수 있다. 진행 표시나 비동기 목록 뽑기가 없다 → 후속 제안.

## 알려진 한계

- 문서의 코드 위치·주소는 이 시점의 코드와 대조해 썼다 (라우트 5개, 모듈 이름). 코드가 바뀌면 문서가 낡을 수 있고, 자동으로 대조하는 장치는 없다.
- `docs/frontend-spec.md` 는 "점수"를 단독으로 쓴 곳이 남아 있다 (화면 문구 기준, #29 PR 참고).
- 실제 TradingAgents-KR 로 웹 처리를 끝까지 돌려 본 적이 없다는 점은 문서에 적었지만 해소되지는 않았다 (쿼터).
- 첫 목록 뽑기가 약 20분 한 요청으로 이어져, 도중에 연결이 끊겨도 서버는 계속하고 세션이 저장된다 (위). README 에는 시간만 적었고 동작은 바꾸지 않았다.
