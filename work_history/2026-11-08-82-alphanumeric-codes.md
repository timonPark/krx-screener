# [feat] 서버가 받게 된 영숫자 종목코드(0126Z0 등)를 보내도록 바꾼다 (#82)

- 브랜치: feat/82-alphanumeric-codes (main 위)
- 작업일: 2026-11-08
- 요청: "네 진행하세요" (이슈 등록과 구현). TradingAgents-KR #181(PR #182)이 2026-11-08 17:40 KST 에 머지되어 서버가 영숫자 코드를 받게 됐다.

## 확인한 것 (읽기 전용, 쿼터 0)

- TradingAgents-KR `origin/main` 의 검증이 `^[0-9A-Z]{6}$` 로 바뀌었다 (분석 요청, 보고서 번호 `^([0-9A-Z]{6})_(\d{8})_(\d{6})$`, 코드 검색).
- 떠 있는 서버(8000)가 이미 새 코드로 재시작되어 있다: `/openapi.json` 의 `RunCreate.ticker` 가 `^[0-9A-Z]{6}$` ("대문자 영숫자 6자, 예: 005930, 0126Z0"), `GET /api/symbols/search?q=0126Z0` 이 `삼성에피스홀딩스` 를 찾는다.

## 수행한 변경

- `analysis.server_accepts`: `^\d{6}$` → **`[0-9A-Z]{6}`** (서버와 같은 규칙). 서버가 거절하는 형식(소문자, 5자·7자, 공백이 붙은 코드)만 "건너뜀" 이다. `\d` 대신 `[0-9]` 를 써서 전각 숫자를 받지 않는다 (이전 PR 에서 발견한 파이썬/화면 차이도 해소).
- `analysis._REPORT_ID_RE`: 서버의 보고서 번호가 영숫자 코드를 담게 되어 같이 바꿨다. 안 바꾸면 영숫자 종목의 `report_saved` 번호와 끝난 보고서(#75)를 믿지 못해 버린다.
- 건너뜀 사유 문구: "서버가 받는 종목코드(대문자 영숫자 6자)가 아니라 보내지 않았습니다."
- 같은 규칙을 쓰는 곳이 자동으로 따라간다: 웹 `process-failed` 대상, 명령줄 대기열 등록(영숫자는 `pending`), `analyze` 의 대상·상태 이름·건너뜀 개수 문구, 화면의 `serverAccepts`(`retry.ts`)와 힌트 문구, 예시 모드.
- 문서: `CLAUDE.md`(서버가 영숫자 코드를 받는다), `README.md`, `GLOSSARY.md`, `docs/backend-design.md`, `docs/frontend-spec.md`, `frontend/README.md`.

## 설계 결정

- 규칙은 서버가 `/openapi.json` 에서 알려 주는 패턴을 **우리가 복제**해 둔 것이다. 읽어서 맞추는 방식은 하지 않았다 (이슈에서 정한 대로, 필요하면 별도 이슈). 복제가 어긋나지 않게 `tests/test_frontend_contract.py` 가 파이썬·화면 두 구현을 같은 코드들(영숫자, 소문자, 5자·7자, 전각 숫자, 줄바꿈)로 대조한다.
- 이미 실패로 기록된 건(DB)의 옛 사유("숫자 6자리 종목코드만 받아…")는 건드리지 않았다. 다시 처리하면 `mark_done` 이 사유를 지운다 (테스트로 확인).

## 이슈에 없던 결정

1. `_REPORT_ID_RE` 도 영숫자로 넓혔다 (위). 요청한 기능이 동작하는 데 꼭 필요해서다.
2. 기존 테스트에서 "서버가 거절하는 코드" 의 예를 `0126Z0` 에서 **소문자 `0126z0`** 로 바꿨다 (서버 스키마는 대문자만 받는다). 소문자를 서버가 실제로 어떻게 다루는지는 보내 보지 않았다 (아래).
3. `CLAUDE.md` 의 한 줄을 고쳤다 ("서버는 숫자 6자리만 받아서…" → 영숫자 6자를 받는다). 사실이 바뀌어서다.

## 하지 않은 것

- **영숫자 종목의 실제 분석.** 실패 2건(0126Z0 삼성에피스홀딩스, 0088M0 메쥬)을 새로 분석하면 쿼터 2번, 약 10분이 든다. 화면의 "실패한 종목 다시 처리" 로 사용자가 누를 때 한다. 개발 DB 는 바꾸지 않았다.
- 서버 규칙을 `/openapi.json` 에서 읽어 맞추는 방식.
- `CLAUDE.md` 의 "에이전트별 등급은 서버와 같은 컴퓨터의 상태 로그 파일에서 읽는다 (API 로는 받을 수 없다)" 문장은 TradingAgents-KR #174 로 이미 사실이 아니지만 이 이슈와 무관해서 고치지 않았다 (알린다).

## 검증 결과

- 테스트를 먼저 썼다: 규칙과 문구를 바꾼 뒤 구현 전에 **9개가 실패**했고, 보고서 번호 테스트 2개를 더한 뒤에도 구현 전 실패를 확인했다.
- `ruff check src tests` 통과, `pytest` **919 passed** (실제 Chrome 브라우저 테스트 포함), `npm run typecheck`·`npm run lint` 통과.
- 변이 검사(복원 확인): 서버 코드 규칙을 숫자만으로 되돌리면 5개, 보고서 번호 규칙을 되돌리면 2개, 화면 규칙을 되돌리면 2개 실패.
- 새로 고정한 동작: 영숫자 코드를 `run_one` 이 서버에 보낸다 / 대기열이 영숫자를 `pending` 으로 둔다 / `process-failed` 가 영숫자 실패 종목을 다시 보내고 옛 사유가 지워진다 / 영숫자 보고서 번호를 믿는다 / 소문자는 여전히 건너뜀.
- 작업 중 실수: 변이 검사 뒤 `git checkout -q frontend/src/retry.ts` 로 변이를 되돌리려다 **커밋 전 변경까지 되돌려** 화면 규칙이 옛 값으로 돌아갔다. 곧바로 알아차려 재적용했고, 변경 파일 목록과 `retry.ts` 의 규칙을 다시 확인했으며 위 검증은 그 뒤 상태의 전체 실행 결과다.
- **확인하지 못한 것**: 영숫자 코드의 **실제 분석이 끝까지 되는지** (데이터 공급자 지원, 쿼터), 서버가 소문자 코드를 어떻게 다루는지 (스키마는 대문자만), 화면에서 버튼을 눌렀을 때의 종단 동작.
