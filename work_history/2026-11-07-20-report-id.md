## 수행한 변경

- `analysis.py`:
  - `AnalysisClient.report_id(run_id)` 신규 — 서버의 진행 이벤트(`GET /api/runs/{run_id}/events`, SSE)에서 `report_saved` 이벤트의

- `processing.py`: 끝난 종목을 저장할 때 `report_id` 를 같이 저장한다. 서버의 실행 번호(`run_id`)는 저장도 노출도 하지 않는다.
- `externals.py`: `AnalysisServer` 경계에 `report_id` 추가.
- 테스트: `test_analysis.py` +14 (이벤트 읽기·bytes·깨진 줄·잘못된 모양·오류·진짜 requests 로 로컬 SSE 서버 읽기), `test_process_api.py` +6
  (저장·노출, run_id 비노출, 실패 종목은 번호 없음, 번호만 못 읽어도 등급 저장, 보고서 없이 끝난 경우, 재분석 성공 시 교체),
  `fakes.py` 에 `report_ids`·`report_error`, `test_analyze_command.py` 의 가짜 서버에 `report_id`.

## 조사 결과: 보고서 번호를 어떻게 얻는가 (이슈 완료 조건)

TradingAgents-KR 소스(`api/runner.py`, `api/run_store.py`, `api/routes/runs.py`, `api/routes/reports.py`, `api/reports_store.py`)를 읽었다.

| 방법 | 내용 | 결론 |
|---|---|---|
| 상태 스냅샷 `GET /api/runs/{id}` | 응답 모델에 `report_id` 가 없다 (status·decision·error·reports 등) | 불가 |
| **진행 이벤트 `GET /api/runs/{id}/events`** | 러너가 보고서를 저장한 직후 `{"type":"report_saved","report_id":<폴더 이름>}` 을 내고 **그 다음에** `done` 을 낸다. 이벤트는 실행 상태에 기록되어, 늦게 붙어도 처음부터 되풀이하고 `done`/`error` 에서 끝난다 | **선택** |
| 보고서 목록 `GET /api/reports` | `report_id`·종목코드·저장 시각·등급 목록. 실행과 이어지는 값이 없다 | 쓰지 않음 |

선택 이유: (1) `report_saved` 는 **이 실행**의 번호를 정확히 준다. (2) 목록 방식은 종목코드로 찾아야 하는데 같은 종목의 보고서가 여러 개 있을 수 있고
(실제로 `~/.tradingagents/logs/reports` 에 `028050_20261106_172435`, `028050_20261106_175036` 두 개가 있다) 번호의 시각은 **저장한 시각**이라
기준일과도 이어지지 않아 어느 것이 이번 분석인지 가릴 수 없다. (3) `report_saved` 가 `done` 보다 먼저 나오므로 스냅샷이 `done` 인 시점에는
이벤트 안에 이미 있다. (4) 서버와 같은 컴퓨터라는 전제(#21)가 필요 없고 HTTP 만 쓴다.

번호 모양: `^\d{6}_\d{8}_\d{6}$` (종목코드_저장일_저장시각). 이 모양이 아니면 신뢰하지 않고 저장하지 않는다 (경로처럼 쓰일 수 있는 값이라서).

## 설계 결정 (이슈 #20 범위 안에서 내가 정한 것)

- **번호를 못 읽어도 실패로 만들지 않는다.** 등급은 쿼터를 들여 얻은 결과라서, 번호 조회가 막혔다고 지우지 않는다. 번호만 빈다.
- **이벤트는 bytes 로 받아 UTF-8 로 직접 디코딩**한다. `text/event-stream` 은 charset 이 없어서 `requests` 가 ISO-8859-1 로 읽으면 한글이 깨진다
  (진짜 `requests` 로 확인). 번호는 ASCII 라 영향이 없지만 깨진 문자열을 파싱 경로에 두지 않았다.
- 분석이 끝난 뒤에만 부른다 (진행 중에 부르면 `done` 까지 스트림이 열려 있다).
- 옛 SQLite 대기열 CLI(`analyze`)는 번호를 저장하지 않는다 (#12 에서 Postgres 저장소로 교체).

## 검증 결과

- `pytest`: 테스트 DB 연결 시 **418 passed** (이전 396), `ruff` 통과.
- 변이 검사: bytes 처리 제거 → 해당 테스트 실패, 번호를 저장하지 않게 → API 테스트 2개 실패, 모양 검사 제거 → 4개 실패. 확인 후 원복.
- 진짜 `requests` 로 로컬 HTTP 서버가 주는 SSE(charset 없음, 한글 포함)를 읽어 번호를 얻는 것까지 확인.
- 완료 조건 대조: 완료된 종목에 `report_id`(예: `028050_20261106_172435`)가 저장된다 ✓ (가짜 서버, API 경계) / 조사 결과와 이유 ✓ (위).
- **실제 TradingAgents-KR 서버로는 확인하지 못했다.** 작업 중 서버가 꺼져 있었고, 끝난 실행을 만들려면 분석 1회(약 5분·쿼터)가 필요해서
  돌리지 않았다. `report_saved` 의 모양은 서버 소스와 디스크의 보고서 폴더 이름으로 확인했다.

## 알려진 한계

- 서버가 재시작되면 실행 상태(이벤트 포함)가 사라져 404 가 되므로 번호를 읽지 못한다. 분석이 끝난 직후에 읽기 때문에 보통은 문제가 없다.
- 실제 서버 이벤트의 모양이 소스와 다르면 번호가 비게 된다 (등급은 저장된다). 실제 분석을 한 번 돌릴 때 `report_id` 가 채워지는지 확인하면 된다.
