# [feat] 실패로 기록됐지만 서버에서는 끝난 종목을 다시 처리할 때 쿼터 없이 가져온다 (#75 남은 부분)

- 브랜치: feat/75-recover-finished-analysis (main 위)
- 작업일: 2026-11-08
- 요청: "#75 남은 부분 진행하세요". 이슈 #75 의 남은 일(제안 3번: 이미 실패로 기록된 건을 구하기)이다. 재발 방지는 PR #78 에서 끝났다.

## 정한 것 (사용자 결정, 2026-11-08)

1. 위치: **"실패한 종목 다시 처리" 안에 둔다.** 버튼·API 는 늘리지 않는다. 종목마다 먼저 서버의 끝난 보고서를 찾고, 없을 때만 새로 보낸다.
2. 같은 종목·기준일의 보고서가 여럿이면 **가장 최근(저장 시각이 가장 늦은) 것**을 쓴다.

## 왜 이제 가능한가

TradingAgents-KR #171~#174 가 모두 머지됐다 (2026-11-08). 특히 #174 는 `GET /api/reports?ticker=&trade_date=&limit=` 에 `trade_date` 와 `agent_ratings` 를 준다. 그래서 `run_id` 를 몰라도 (저장하지 않는 규칙을 건드리지 않고) 서버에 끝난 분석이 있는지 찾을 수 있다.

## 수행한 변경

- `analysis.py`: `FinishedReport`(보고서 번호·최종 등급·에이전트별 등급), `AnalysisClient.find_finished_report(ticker, trade_date)`.
  - 응답에서 **종목·기준일을 직접 다시 확인한다.** 필터를 모르는 옛 서버는 다른 종목도 주고 `trade_date` 가 없어서 → "없음" (예전처럼 새로 분석).
  - 최종 등급이 5단계 값이 아니거나 보고서 번호가 올바르지 않은 행은 건너뛰고, 남은 것 중 `stamp` 가 가장 늦은 것을 쓴다.
  - 목록을 읽지 못하면(404·5xx·깨진 응답·연결 실패) 경고만 남기고 "없음"이다: 이 확인 때문에 다시 처리가 막히지 않는다 (`find_running` 과 같은 태도).
- `processing.py`: `recover_item`(보고서 결과를 완료로 저장), `process_codes(..., recover=False)`. `recover=True` 면 종목마다 먼저 `find_finished_report` 를 보고 있으면 새로 보내지 않는다. 알 수 없는 에이전트·5단계에 없는 값은 버리고, 점수는 `score_ratings` 로 계산한다. 분석 시간을 재지 않았으므로 `elapsed_seconds` 는 건드리지 않는다 (예상 시간 평균을 흐리지 않게).
- `routes_sessions.py`: `process-failed` 만 `recover=True`. 구간 처리(`/process`)는 그대로다 (대기 종목은 새로 분석).
- 화면: 힌트와 확인창 문구만 바꿨다 ("서버에 이미 끝난 분석이 있으면 쿼터 없이 가져오고, 없는 종목만 새로 분석합니다"). 로직은 백엔드에 있다.
- 문서: `docs/backend-design.md`(13장 #75 항목의 한계를 해결로 바꿈, 처리 규칙), `docs/frontend-spec.md`, `README.md`, `analysis.py`·`processing.py` 설명.

## 설계 결정

- 응답 모양은 그대로다 (`202 {"started", "queued"}`). `queued` 는 "처리할 종목 수"이고 그중 일부는 쿼터 없이 가져올 수 있다. 확인창은 "쿼터 최대 N번" 이라고 한다 (가져온 만큼 적게 쓴다).
- 가져오기는 새로 만드는 보고서가 아니라 **서버가 이미 가진 결과를 읽는 것**이라 로컬 상태 로그(덮어써진다)를 읽지 않는다. 같은 종목·기준일을 다시 분석해도 서버의 보고서는 시각별로 따로 남으므로 "가장 최근"이 의미 있다.
- 가져온 종목은 `analyzed_at` 이 가져온 시각(지금)이다. 분석을 실제로 한 시각이 아니다 (보고서 번호의 시각이 저장 시각이다).

## 이슈에 없던 결정

1. 가져온 종목의 `analyzed_at` 은 가져온 시각이다 (분석 시각을 보고서 `stamp` 로 쓰려면 서버 시각대(KST 로컬) 변환이 필요해서 하지 않았다).
2. 옛 서버(필터·`trade_date` 없음)에서는 조용히 예전처럼 새로 분석한다. 화면은 서버 버전을 모르므로 문구에 "서버가 새 버전이어야 한다"를 넣지 않았고 README·설계 문서에 적었다.
3. 설정(`effort` 등)이 다른 분석(서버 화면에서 직접 돌린 것)도 같은 종목·기준일이면 가져온다 (#70 이 도는 분석을 이어받을 때와 같은 한계).

## 하지 않은 것

- 개발 DB 의 실패 3건(하림지주·서울보증보험·한일시멘트)을 실제로 구하는 일. 사용자가 화면에서 버튼을 누르는 일이고(쿼터 0이어야 하는데 지금 떠 있는 서버가 옛 버전이라 **지금 누르면 쿼터 3번을 쓴다**), 개발 DB 를 바꾸는 일이라 하지 않았다.
- TradingAgents-KR 저장소·실행 중인 서버(8000)에는 손대지 않았다. `pull` 도 하지 않았다 (`--reload` 가 돌고 있는 분석을 끊을 수 있고, 그 서버가 지금 다른 분석을 돌리고 있다).
- `find_running`(#70)을 가벼운 `GET /api/runs` 필터(#171)로 바꾸는 일, 취소 API(#173) 활용, 서버 보고서에서 에이전트 등급을 읽도록 로컬 로그 읽기를 대체하는 일. 요청 밖이라 이슈로 제안만 한다.
