## 설계 결정 (사용자 확정)

- 시범은 후보 3개, `effort: low`, 한 번에 하나씩. 쿼터를 쓰므로 `--limit` 을 필수로 하고 확인을 묻는다.
- **DB 도입은 Q9("DB 는 쓰지 않는다")를 뒤집은 결정이다.** 사용자 제안: 후보 목록을 DB 에 넣고 끝나는 대로
  표시하는 방식. 실행은 그때그때 사용자가 한다. 자동 이어받기·상태 명령·서버 `run_id` 되찾기는 만들지 않았다.
- 최종 등급은 5단계(범주)뿐이고 점수는 없다. 정량 점수(합의도 등)는 100개를 돌린 뒤에 검토하기로 함.

구현 중 정한 것:
- `--redo` 로 다시 분석하다 실패해도 이미 있는 등급은 지우지 않는다 (실패 시 DB 를 바꾸지 않음).
- 후보가 목록에서 빠지면 끝난 기록은 남기고(순번만 뒤로), 끝나지 않은 것은 지운다.
- `--dry-run` 은 서버에 연결하지 않고 분석 상태를 바꾸지 않는다 (후보 목록 등록만 한다).

## 확인한 사실 (TradingAgents-KR)

- API 는 `effort` 하나로 **두 단계(deep/quick)를 모두 덮어쓴다** (`api/runner.py::build_config`). CLI 기본값은
  deep `high` / quick `medium` 이라 API 의 `low` 는 CLI 보다 얕다. 이전에 사용자가 돌린 분석의 effort 는 알 수 없다.
- **토큰 사용량을 기록하지 않는다** (어댑터는 `result`/`structured_output`/`is_error` 만 읽음). 쿼터 소모는 사용량
  화면의 전후 차이로만 알 수 있고, 시범 전 수치를 받아 두지 못했다.
- 서버에는 취소 API 가 없고 `run_id` 상태는 메모리에만 있다. 동시 실행 제한은 없고 모델 호출 세마포어는 기본 2.
- 보고서에는 단계별 `등급`이 11번 나오고(분석가 4·강세/약세·매니저·공격/보수/중립·PM) 점수·목표가는 없다.
- 서버 기록 11건의 분포: 비중 축소 9 · 보유 2. 같은 종목 재분석 2건(알테오젠 1일 간격, 펩트론 같은 날 3회)은
  등급이 같았다 — 표본이 작아 안정적이라고 말할 수 없다.
