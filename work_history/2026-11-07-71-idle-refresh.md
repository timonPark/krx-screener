# [feat] 쉬는 중인 화면도 다른 곳이 시작한 처리를 알아챈다 (#71)

- 브랜치: feat/71-idle-refresh (main 위)
- 작업일: 2026-11-07
- 요청: #71 ("#71 진행하세요"). 설계안을 보여 드렸고 사용자가 **저빈도 폴링 + 탭 복귀 시 조회**, **지금 조회 그대로**(가벼운 API 추가 안 함)로 정했다.

## 수행한 변경

- `frontend/src/app.ts`
  - `scheduleRefresh()`: 만드는 중 2초 · 처리 중 10초(둘 다 지금과 같다) · **쉬는 중 `idlePollMs`(30초)**. 처리가 끝나도 멈추지 않고 쉬는 중 확인으로 돌아간다.
  - 쉬는 중 확인은 **탭이 보일 때만**: 예약 시점에 숨겨져 있으면 예약하지 않고, 기다리는 동안 숨겨졌으면 부르지 않고 멈춘다. 다시 보이면 `visibilitychange` 가 바로 한 번 조회하고 이어 간다 (동작 중이면 건너뜀).
  - **조회 순서 보호**: 조회를 보낼 때마다 번호를 올리고 가장 최근에 보낸 조회의 응답만 반영한다 (`refreshSeq`).
  - 상태 문구: 쉬는 중이면 `마지막 갱신 HH:MM:SS · 30초마다 확인`.
- `frontend/src/config.ts`: `idlePollMs: 30_000` (0 이면 끔). 예시 모드는 끈다 (화면 밖에서 데이터가 바뀌지 않는다).
- 브라우저 테스트: 시나리오 2개 — `startedElsewhere`(화면을 열어 둔 채 화면 밖 API 로 처리를 시작 → 새로고침 없이 "처리 중" → 끝난 뒤에도 쉬는 중 확인으로 돌아가 다음 처리도 알아챔), `hiddenTab`(숨긴 탭은 조회하지 않고 다시 보이면 바로 한 번 조회). 테스트 서버가 `idlePollMs` 를 1.5초로 바꿔 내려준다.
- 문서: `docs/frontend-spec.md`(5장 갱신 규칙, 설정 표), `docs/backend-design.md`(13장 한계), `frontend/README.md`.

## 설계 결정

- 기존 API 그대로 쓴다 (사용자 결정): 쉬는 중 확인도 세션 조회를 쓴다. API·응답 필드 변경 없음.
- `visibilitychange` 만 듣는다 (`focus` 는 듣지 않는다): 탭 전환·최소화·가려짐은 `visibilitychange` 로 잡히고 다른 앱 창을 오갈 때는 30초 확인이 잡는다. 둘 다 들으면 탭 전환마다 요청이 둘이 된다.
- 숨겨진 동안은 타이머를 멈추고(다시 걸지 않는다) 복귀 때 이벤트로 재개한다: 숨긴 탭이 백그라운드 타이머를 계속 돌리지 않는다.

## 이슈에 없던 결정

1. **조회 순서 보호(`refreshSeq`)**: 쉬는 중 폴링이 늘면 폴링 응답이 버튼 동작 뒤의 응답보다 늦게 도착해 옛 상태를 덮어쓸 위험이 커져서 같이 넣었다 (이전에도 처리 중 폴링에서 가능했다).
2. 쉬는 중 상태 문구에 `· 30초마다 확인` 을 붙였다 (자동 확인이 켜져 있음을 알린다).
3. 세션이 하나도 없을 때와 다른 곳에서 새 세션을 만든 경우(세션 목록)는 확인하지 않는다 (이슈는 "보고 있는 세션의 처리 상태").

## 알려진 한계

- **조회 순서 보호(`refreshSeq`)는 변이 검사로 확인하지 못했다.** 겹친 조회에서 늦게 온 옛 응답을 버리는 것을 재현하는 브라우저 테스트가 없다 (응답 지연을 만들어야 한다).
- 쉬는 중 확인마다 세션 전체를 내려받는다 (크기·시간은 측정하지 않았다). 비용이 문제로 보이면 가벼운 상태 API 를 이슈로 남긴다.
- 다른 곳에서 만든 새 세션은 새로고침해야 보인다. 세션이 하나도 없을 때도 확인하지 않는다.
- 숨겨진 탭 판정은 `document.visibilityState` 이고 테스트는 이 값을 덮어써서 흉내 냈다 (실제 탭 전환·최소화로 확인하지는 않았다).
- 실제 TradingAgents-KR 로는 확인하지 않았다 (분석 쿼터를 쓸 필요가 없어서 가짜 분석 서버로 처리를 시작했다).
