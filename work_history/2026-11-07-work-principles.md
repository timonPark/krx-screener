## 수행한 변경

- `CLAUDE.md` 에 "작업 원칙" 섹션을 추가했다 (10줄 추가, 기존 줄 삭제·수정 없음). "작업 규칙" 바로 아래, "i18n 경계" 위.
- 원문(영어 4개 원칙)을 그대로 붙이지 않고 이 프로젝트에 맞게 줄이고 바꿨다:
  1. **가정은 밝히고, 큰 결정은 먼저 묻는다** — 묻는 경우를 한정했다: 되돌리기 어렵거나 밖으로 나가는 일(머지·삭제·이슈 생성·사용자 DB 변경), 쿼터를 쓰는 일, 설계가 바뀌는 선택(스키마·API 필드·명령의 의미).
     그 밖의 모호함은 가정을 적고 진행하고 PR 의 "이슈에 없던 결정"에 남긴다.
  2. **요청한 것만 만든다** — 요청 밖 기능은 이슈로 제안, 요청한 기능이 안전하게 동작하는 데 꼭 필요한 것만 예외로 두고 PR 에 밝힌다.
  3. **무관한 것은 건드리지 않는다** — 무관한 문제는 알리거나 별도 `chore` PR (예: #54 import 정렬).
  4. **성공 기준을 먼저 정하고 검증한 만큼만 말한다** — 원문에 없는 부분이다: 실행하지 않은 검증을 "했다"고 쓰지 않고, 측정하지 않은 값은 단정하지 않는다.

## 알려진 한계 / 효과 확인 계획

- 두세 개의 PR 을 본 뒤 다음 신호로 조정한다: PR 의 "이슈에 없던 결정" 항목이 줄었는가, 요청과 무관한 파일 변경이 줄었는가, 질문이 구현 전에 나왔는가, "못 한 것"이 빠짐없이 적혔는가.
- 질문 기준이 너무 엄격하면 진행이 느려질 수 있고 너무 느슨하면 효과가 없다. 어긋나는 것이 보일 때 한 줄씩 고친다 (처음부터 규칙을 많이 두지 않았다).
- "PR 의 '이슈에 없던 결정'" 은 지금까지 PR 본문에서 쓴 관례이고 PR 템플릿(`pr` 스킬)에 있는 항목은 아니다.
