## 수행한 변경

- `src/krx_screener/agent_ratings.py` 신규: `read_agent_ratings(root, code, as_of)` — 서버의 분석 상태 로그
  (`{root}/{종목}/TradingAgentsStrategy_logs/full_states_log_{기준일}.json`)에서 에이전트 10개의 칸을 읽어 `에이전트 → 등급(영어 내부값)`
  을 돌려준다. `parse_rating(text)` 는 한 칸의 글에서 등급을 읽는다. 읽지 못한 에이전트는 빠진다.
- `processing.py`: 분석이 **끝난 직후** 로그를 읽고, 완료 표시와 에이전트별 등급을 **한 트랜잭션**으로 저장한다
  (`save_agent_ratings` 가 옛 행을 새 값으로 통째로 교체). 이전에 남아 있던 옛 에이전트 등급은 재분석 성공 시 사라진다 (#19 핸드오프).
- `externals.py`: 문서의 `state_log_root` 설명 갱신. `docs/backend-design.md`: 확인 결과 반영.
- 테스트: `test_agent_ratings.py` 60개(표기 변형·읽지 못하는 글·깨진/없는/다른 로그), `test_real_state_logs.py` 13개(이 컴퓨터의 실제 로그),
  `test_process_api.py` +8, `fakes.py` 의 가짜 서버가 분석을 마치면 실제 서버처럼 상태 로그를 쓴다.

## 조사 결과: 다른 로그에서도 같은 구조인가 (이슈 완료 조건)

`~/.tradingagents/logs` 의 실제 로그 **13개**(종목 9개, 기준일 2024-01-05 ~ 2026-11-06, effort low·high, 분석가 전체·market 만)를 전부 읽었다.

- **구조는 같다.** 최상위 칸 13개와 에이전트 칸 이름이 모든 로그에서 같고, 칸의 값은 모두 문자열이다. `company_of_interest`·`trade_date` 가 파일 이름과 일치한다.
- **정확도 교차 검증:** 포트폴리오 매니저 칸에서 읽은 등급이 로그의 `final_rating` 과 **13개 모두 같다**.
- **칸 안의 글 모양은 제각각이다.** 읽은 표기: `**등급**: 매수`, 영어(`Underweight`)·대문자(`HOLD`, `SELL`), `**등급: 보유.**`,
  `Aggressive Analyst: **등급**: 보유`, `**전략적 조치**: **등급**: 보유 (…)`, 표 `| **등급** | **보유** |`, 리서치 매니저의 `**추천**: 비중 축소`.
- **읽힌 에이전트 수:** 10/10 로그 7개, 9/10 1개(034020 뉴스 칸에 등급 없음), 8/10 1개, 6/10 1개, 4/10 1개(069620: 6개 칸에 `최종 거래 제안`만 있음),
  3/10 1개(2024 년 market 분석가만 돌린 시범 로그). 못 읽은 칸은 모두 실제로 읽을 5단계 등급이 없는 칸이었다:
  분석가를 일부만 돌려 빈 칸, 공격적 분석가가 역할극을 거부한 응답(087010), 5단계에 없는 값 `REDUCE`(087010), `최종 거래 제안`만 있는 칸.
- 한 칸에 서로 다른 값이 나온 경우는 `등급` 라벨만 읽을 때 **0건**이다 (`최종 거래 제안` 까지 읽으면 10칸이 충돌한다 — 아래 결정).

## 설계 결정 (이슈 #21 범위 안에서 내가 정한 것)

- **`최종 거래 제안` 은 읽지 않는다.** 에이전트 글 끝에 `**등급**: 비중 축소` 와 `**최종 거래 제안**: 매도` 가 함께 나온다. 후자는 등급을
  3단계로 뭉갠 값이라 5단계 등급의 대용으로 쓰면 점수가 한쪽으로 치우친다. 그 값만 있는 칸은 비워 둔다.
- **라벨은 줄 머리이거나 `접두 라벨: ` 바로 뒤에서만 인정**한다. 처음에는 라벨 앞에 글자만 없으면 읽게 했는데, "컨센서스 등급: 매수"
  같은 증권사 의견 문장이 에이전트의 등급으로 읽힐 수 있어 조였다 (테스트로 고정). 실제 로그 13개의 결과는 조이기 전과 같다.
- **`추천` 라벨은 리서치 매니저 칸에서만** 읽는다 (030530·087010 의 리서치 매니저는 `**추천**:` 줄뿐이다). 다른 칸의 "추천" 은 등급이 아니다.
- **서로 다른 값이 나오면 비운다.** 어느 쪽이 그 에이전트의 등급인지 알 수 없다. 같은 값이 여러 번이면 그 값이다.
- **로그 안의 종목·기준일이 다르면 로그 전체를 읽지 않는다** (없으면 확인할 수 없으니 읽는다).
- **읽지 못해도 최종 등급은 저장한다.** 로그가 없으면(서버가 다른 컴퓨터) 에이전트별 등급이 비고, 옛 에이전트 등급 행도 지워진다 — 새 분석 결과와
  섞이지 않게. 실패한 분석의 로그는 읽지 않는다 (재분석 실패 시 옛 행이 그대로인 #19 동작 유지).
- 에이전트 수·점수(`agents_rated`, `agents_total`, `score`)는 #22 가 채운다. 이 이슈에서는 에이전트별 등급 행까지만 저장한다.

## 검증 결과

  에이전트별 등급 저장 생략, 엇갈린 값에서 첫 값 선택, 트랜잭션 제거.
- 완료 조건 대조: 실제 로그 모양의 샘플에서 에이전트별 등급이 읽힌다 ✓ / 칸이 비었거나 형식이 달라도 멈추지 않고 그 에이전트만 빈다 ✓
  (null·숫자·목록·깨진 JSON·바이너리·없는 파일) / 다른 로그에서도 같은 구조인지 확인한 결과 ✓ (위).
- 실제 TradingAgents-KR 서버로 분석을 돌려 이 경로(분석 직후 읽기)를 끝까지 확인하지는 않았다 (분석 1회 약 5분·쿼터). 파일 읽기와 파서는 실제
  로그 13개로, 처리 흐름은 가짜 서버가 분석 직후 로그를 쓰는 방식으로 확인했다.

## 알려진 한계

- **서버와 같은 컴퓨터가 전제**다. `state_log_root` 가 서버의 로그 폴더(`~/.tradingagents/logs`, 환경변수 `TRADINGAGENTS_RESULTS_DIR` 로 바뀔 수 있음)를
  가리켜야 한다. 이 폴더를 조립하는 운영 쪽 코드는 아직 없다 (웹 서버 실행 설정을 만드는 이슈에서 정한다).
- 서버가 글 모양을 바꾸면 그 칸이 빈다 (오류로 멈추지 않음). 069620 처럼 5단계 `등급` 줄 없이 `최종 거래 제안` 만 쓰는 응답은 이미 존재하고,
  그 종목은 4/10 만 읽힌다 — 점수가 적은 에이전트로 계산되므로 `등급을 낸 에이전트 수` 를 같이 보여주는 #22 의 설계가 이 경우를 드러낸다.
- 분석이 끝난 뒤 로그를 읽기까지의 사이에 같은 종목·기준일을 다시 분석하는 것은 세션 잠금(#18)이 막지만, 서버를 다른 경로(웹 화면·CLI)로 직접 돌리면
  덮어써질 수 있다. 안의 종목·기준일 확인은 이 경우를 걸러주지 못한다.
